### データベースの場所（`data.py: DB_PATH`）

`DB_PATH` は既定で **`data.py` 自身の位置から `scripts/pokenavi.db` を相対解決**する（`os.path.dirname(os.path.dirname(os.path.abspath(__file__)))`）。
環境変数 **`POKENAVI_DB`** を設定するとそちらを優先する。

以前は開発機の絶対パス固定だったため、コンテナ（Cloud Run）にそのまま載せると起動時に
`sqlite3.OperationalError: unable to open database file` で落ちた。デプロイ可能性のため相対解決が仕様。

## 0-1. 型の書式（`pokemon.parse_pokemon_spec`）
- `種名[@持ち物][:性格][:技1|技2|技3|技4][:H/A/B/C/D/S][:特性]`。
- 種名に「:」を含む種（ケンタロス:炎 等）があるので、`@` があるときは `@` より前をそのまま種名として読む（以前は「:」で区切って努力値の欄がずれ、読み込みに失敗していた）。
- Rust `poke::parse_pokemon_spec` も同じ解析（2026-10-04 監査200 #2。以前は `@` の後ろを種名に連結してから「:」で区切り、ケンタロス:炎 で panic していた）。
  各欄の前後の空白は無視、努力値は値ごとに空白を許す（Python の `int()` と同じ）。読めない努力値は Rust では `parse_spec_checked` が Err（`spec_error` もこれを使う）。
  照合: `pokenavi_engine.parse_spec(spec)` が Python と同じ (種名, 持ち物, 性格, 技, 努力値, 特性) を返す（test_all 40節で型プール全件を比較）。

## 1. わざ（技）

### 1-1. 基本仕様

- ダメージ式: `floor(floor(floor(2×Lv/5+2) × 威力 × 攻撃/防御) / 50) + 2`
- Lv固定: **50**
- 乱数: 85〜100% (均一16段階)
  - 正規化値 `random_roll=x` で指定するとき、x×15 が整数（16段のどれか）なら実戦と同じ `(85+k)/100` を使う（`0.85+x*0.15` は浮動小数の丸めで 0.91→0.90999… となり、切り捨てで実戦の値と1ずれる。信念の観測照合が正解の型を潰していた）。それ以外の x（平均ロール 0.5 等）は `0.85+x*0.15`。Rust `damage.rs` も同じ
- タイプ一致補正 (STAB): ×1.5、てきおうりょく特性時 ×2.0
- 急所倍率: ×1.5、ランクによる確率は下表

| 急所ランク | 発動確率 |
|-----------|--------|
| 0 (標準) | 1/24 |
| +1 (高急所技) | 1/8 |
| +2 (きあいだめ等) | 1/2 |
| +3 以上 | 確定 |

**急所命中時の追加効果（ダメージ×1.5 に加えて）:**
- 攻撃側の攻撃・特攻ランクが**マイナス**の場合、そのランク変化を無視してダメージ計算（プラスのランクは有効）
- 防御側の防御・特防ランクが**プラス**の場合、そのランク変化を無視してダメージ計算（マイナスのランクは有効）

高急所技（ランク+1）: きょうふのつるぎ / からじしボム / フリーズドライ / スラッシュ / カタストロフィ / シャドークロー / ナイトスラッシュ / クロスポイズン / サイコカッター / リーフブレード / ３ぼんのや / ストーンエッジ / ブレイズキック / クラブハンマー / クロスチョップ / つじぎり / ドリルライナー / アクアカッター / エアカッター / ゴッドバード

### 1-7. 2ターン溜め技

1ターン目は「溜め」、2ターン目に攻撃。以下の例外あり：
- ソーラービーム / ソーラーブレード: **晴れ中は即時発動**
- エレクトロビーム: **雨中は即時発動**
- 溜め中に**ねむり**で行動できなくなると溜めは解除される（起床後に発火しない＝技を選び直す）。交代でも解除（`charging_move` クリア）。
- **姿を消す溜め技の1ターン目は相手の技が当たらない**（2026-10-04 監査200 #11。`damage.semi_invulnerable_miss`）。相手を対象にとる技（攻撃技・`FOE_STATUS`）が対象。
  そらをとぶ・とびはねる 中は かみなり・ぼうふう・うちおとす・サウザンアロー・スカイアッパー・たつまき・かぜおこし、あなをほる 中は じしん・マグニチュード・じわれ、
  ダイビング 中は なみのり・うずしお だけが当たる（じしん・なみのり は2倍）。ゴーストダイブ 中は何も当たらない。ノーガード（どちらか）・ロックオン は当たる。

### 1-14. あばれ状態

使用すると「あばれ状態」になり、強制的に同じ技を連続で使い続ける。

| フェーズ | 処理 |
|----------|------|
| 初回使用 | `locked_move` に技名をセット、`lock_count` を 2〜3 にランダム設定 |
| 継続ターン | 同じ技を強制使用。`lock_count` を 1 減らす |

- あばれ状態中（`lock_count > 0`）は他の技を選択不可（UI・AI ともに無効化）

## 4. バトルシステム全体仕様

### 4-0. 分析（1v1判定）用の差込口

対戦本体の挙動は変えずに、分析側だけが前提を固定するための差込口を2つ持つ。
既定値では対戦と完全に同じ動作になり、分析中だけ `_mu_engine._enter_fixed()` が差し替える。

| 差込口 | 既定 | 分析時 | 目的 |
|---|---|---|---|
| `damage._ROLL_OVERRIDE` | `None`（16段の乱数） | `0.0`〜`1.0` | 与ダメの下限・上限を出す |
| `battle._HIT_CONTINUE` | `None`（`random.random`） | `lambda: 0.0` | ネズミざんの「もう1発続くか」を必中扱いにする |
| `battle._MULTI_HIT_FIXED` | `None`（重み3:3:1:1の抽選） | `3` | 2〜5回の連続技を期待値の3回に固定する |
| `battle._ASSUME_OPP_ATTACKS` | `False` | `True` | ふいうちを「相手が攻撃してくる」前提で通す |

`_HIT_CONTINUE` は、**1発ごとに命中判定があり外れるとそこで止まる技**（`battle.ACCURACY_CHAINED`
＝トリプルアクセル・ネズミざん）のための差込口。分析は `check_hit` を必中に固定するので、
これらの技も最大回数まで当たる扱いに揃える。揃えないとネズミざんだけ「1発しか当たらない前提」
になり、主力技が圏外と出る。表示側はこの前提を「最大ヒット時」と注記する。

回数そのものが乱数で決まる技（みずしゅりけん等の2〜5回）は重み3:3:1:1で**期待値がちょうど3.0**
なので3回に固定する。最小の2回では過小、最大の5回では過大で、幅で示すと4回・5回が各12.5%しかない
という分布の偏りを誤解させる。スキルリンク持ちは `calc_hits` が先に5回と決めるのでそのまま。
表示側は「3ヒット時」「最大3ヒット時」のように何発当たる前提かを注記する。

**分析の対象から外す技**: `battle.COUNTER_MOVES`（カウンター・ミラーコート・メタルバースト）は
相手が出した技の種類と威力で威力が決まるため、成功前提で評価すると過大になる。
1v1判定の「最大打点1発」の候補から除外する（対戦本体では通常どおり動く）。

#### 4-0-1. 1v1判定の本体：方針の組ごとの2者対戦（Rust `analysis.rs::verdict_sim`、2026-09-27）

記号・勝敗・先後・手数（`verdict` の `sym/score/win/fast/koFirst/myHits/oppHits/myS/oppS`）は、
**両者が同時に行動する実際の対戦**（`sim_pair`）から決める。以前は各側を「相手は棒立ち」で個別に数えた確定数と
初期素早さで決めていたため、積み技・ねこだまし・かるわざ・自分の能力が下がる技（からをやぶる・インファイト）・
スケイルショットの素早さ上昇・ゆきなだれ・ゴツゴツメット/反動の削りなど、互いの行動が影響し合う要素を表せなかった。

- **各側の方針（候補）**: (1) 最大打点技（棒立ちで数えた発数が最少の技）を撃ち続ける
  (2) 毎ターン、その時点の局面で最善の攻撃技を選び直す（`best_attack`。暴れ技を避ける線は棒立ちの手順と同じ選び方）
  (3) 準備の1手→攻撃：1ターン目に準備の技を**1回だけ**使い、2ターン目以降は(2)。準備の技は
  積み技（`self_boosts` に正の段階を持つ技すべて。命中・回避だけを上げる技は必中前提の判定では効果が無いので除く）と
  ねこだまし（タイプ無効等で当たらないときは「何もしない方針」になるので除く）。
  (4) 持久戦（どくどく・おにび を持つ側）：相手が状態異常でなく、その技で実際に状態異常が入るなら（1ターン実走で確認）状態異常の技、
  相手の最善の攻撃で倒されそうで、先に動けて回復で耐えられるなら回復技、それ以外は(2)と同じ最善の攻撃技（まとわりつく等の拘束技も
  ターン終了時の削り込みの見込みで選ばれる）、攻撃技が無ければ回復技。以前の「持久戦ルート」（相手を棒立ちにした別計算で記号を ○/▲ に上書き）は廃止し、
  記号・勝敗・経過（棒・再生）はすべてこの方針を含む同じ対戦から出す。持久戦の方針がある対面は、毒で削り切るまで見るため
  全ての方針の組で上限を20ターン（`STALL_CAP`）にする。
  「この状況なら」の積み指定がある側（自分 `scenario.boost>0`／相手 `scenario.opp_boost>0`）は、積み技を準備の手にしない（二重計上の防止）。
  積み指定は `apply_scenario` がその側の技欄の先頭の積み技の段階を最初から入れる（相手側は工房の「積み（相手）」。pyengine は `mu_analyze_scenario`）。
- **対戦の前提**: 中央乱数（0.5）・必中・確率の追加効果は不発・確定の追加効果は発動（固定乱数）。
  先後は毎ターンの実際の素早さと優先度、能力変化・持ち物の消費（ノーマルジュエル→かるわざで素早さ2倍）・
  ひるみ（ねこだましで相手の1ターン目の行動が消える。ゴーストには当たらず、せいしんりょくはひるまない）・
  へんげんじざい/リベロの型変化（実際に技を撃った時点）・天候・回復は全て対戦本体の処理のまま。上限は5ターン（持久戦の方針がある対面は20ターン）。
  **倒れたターンもターン終了時処理まで進める**（`Field.eot_on_last_faint`。分析専用）：1v1判定は6体戦の中の1対面なので、実機どおり
  片方が倒れたターンでも生き残った側にはそのターンのもうどく・どく・やけど・天候・たべのこし等が入る（倒れた側の効果は除く。
  拘束は縛った側が倒れたら解ける）。対戦本体は最後の1体が倒れた時点で対戦が終わる（実機どおり）ので、この設定は使わない。
  例: ドヒドイデ vs メガボーマンダは どくどく（T1終わり1/16）→ 倒される → T2終わりのもうどく2/16 まで入り、まとわりつく（縛った側が倒れると解ける）より削れる。
- **手数**: 各側が相手を倒したターン。先に倒された側の手数は「倒されなかったら何ターン目に倒せたか」で、
  倒されたターンの開始局面から、倒された側に「倒れても行動し続ける」印（`Poke.undying`。分析専用・対戦本体は常に無効）を付けて同じ方針で続けた値
  （2026-09-27 に最大HP×64の水増し方式から置き換え）。HPは本物のまま0で止まるので、ふんか/しおふき・オボンのみ・マルチスケイル・
  きあいのタスキ・もうか等のHPで決まる要素は実際どおり（例: ふんかは0で威力が落ちる）。勝った側への反動も実際に減らしたHPが基準のまま（水増しで膨らまない）。
  方針の手の選択だけは「負けた側がまだ十分なHPで場にいる」前提で行う（0のまま選ぶと勝った側が攻撃しなくなる）。
  勝った側が倒れたターンは、倒された側が生きていたら起きること（技・ゴツゴツメット・さめはだ・反動・いのちのたま・天候・毒等）で倒れたら数え、
  勝った側が自分の技で倒れた（だいばくはつ・ミストバースト等、原因の記録が無いまま0になる）ときは数えない。
  上限（5ターン、持久戦の方針があれば20ターン）で倒せなければ圏外（999）。
- **勝者**: 誰かが倒れたターンの終わり（ターン終了時処理の後）で決める。片方だけ倒れていれば生き残った側の勝ち
  （技で倒されずに反動等で自滅した側は負け）。両者が倒れていれば**相打ち**（相手を技で倒した行動の反動・いのちのたま・ゴツゴツメット等で直後に自分も倒れた場合、
  相手を倒した後のそのターンのターン終了時に毒・天候等で自分も倒れた場合、ターン終了時に両者が倒れた場合）＝引き分け扱いでスコア0
  （`mutual: true`、判定文「相打ち：Nターン目に互いに倒れる」）。6体戦の中の1対面として、同じターンに1体ずつ失う交換は五分と見る
  （実機で最後の1体どうしなら先に倒れた側の負けで対戦が終わるが、判定は途中の1対面を想定するため）。
  表示の ✕ は技で相手を倒したときに付け、相手が反動等で倒れたときは別の色の ✕（縞の末尾）にする。
- **ダメージ乱数**: 判定（記号・勝敗・帯・判定文・経過・手数・素早さ）はすべて**中央乱数（0.5）の対戦1本**で決める（期待値として最低乱数より妥当）。
  最低・最高乱数での対戦は回さない（以前は勝敗が割れると「乱数次第」と注記していたが、中央だけで記号が決まり注記は判定を変えないため外した。
  `rollDep`・`rollOutcomes`・`rollScores` は出力しない）。出力スコアは記号の範囲 ±2 にクリップする
  （圏外999の差がそのまま入ると、型ごとの重み付き平均で極端に効くため）。技ごとの確定数は中央乱数で数えた `hitsMid` を主表示にし
  （最低乱数でも同じなら「確定n」、違えば「乱数n発（n発以内に倒せる確率）」）、最低〜最高は技ごとのダメージ幅に残す。最大打点技の選択も `hitsMid` で比べる。
- **技の選び方**（最大打点技・毎ターン最善手・準備後の攻撃・表示用の最大打点で共通）: 倒すまでのターン数 → （倒せる手どうしは先制技）
  → 自分への不利益が無い技（反動・いのちのたま以外の自傷・自分の能力低下・溜め/反動で動けない/暴れ技のロックを、1ターン実走して測る）
  → 命中率 → 火力。例: メガボーマンダは じしん でもオオニューラを確1なので すてみタックル を選ばない。エンジンは選んだ技に `best: true` を付け、表示側はそれを最大打点技として使う。
- **方針の比べ方**: 行列の各マスは (勝ち/相打ち・引き分け/負けの区分, 相手の残りHPの少なさ, 自分が倒れるまでのターン, 自分の残りHP, スコア(±2クリップ)) の辞書順
  （自分の残りHPは、最後の一撃を反動の無い技で決める線を選ぶため）。最大打点技の選択も、1発で倒せる技どうしは先制技を優先する。
  おやこあい の技の表示ダメージは2発目（1発目の25%）を含む。
  反実仮想の手数差（倒されなかったら何ターンで倒せたか）は最後のタイブレークだけ（先に使うと、負けが確定の側が積み・不発のねこだまし等
  「何もしない方針」を選んでいた）。同速で両順を回したマスは、残りHP・倒れたターンも両順の平均で比べる。
  毎ターン最善手の「削り」は技のダメージで測り、防御側がそのターンに食べたきのみ(オボンのみ等)の回復は差し引かない。
  記号が同じ方針どうしは、相手を多く削り長く粘る方を選ぶ（負けが確定でも ねこだまし 等で最善を尽くす経過を出す）。
- **同速**: 行動順が同速の先後で決まるターン（対戦本体の `speed_order` を先後を両方に固定して呼び、結果が割れるか。特性・場による優先度補正込み）が
  あった組は、自分が先・相手が先の両方の順で回し（`Field.speed_tie_p1_first`。分析専用で対戦本体は乱数のまま。開始局面の入場効果・メガシンカの順にも効かせ、
  開始局面の作り置きのキーに含める）、判定の先後（fast）もその対戦で回した順で決める（(a,b) と (b,a) のスコアは符号だけが逆になる）。
  スコアを平均する。結果が順で変わるときは `tie: true` とし、表示は先手/後手の代わりに「同速（先後は半々）」、経過(race)は自分が先の場合を代表にする。
- **スコア**: 組ごとに `score_of(自分の手数, 相手の手数, 先に倒した側, …)`。手数が同じなら実際に先に倒した側が勝ち。
  決着ターン開始時の実効素早さを `myS/oppS`・`fast` にする（積んだ後・かるわざの後の値）。
- **方針の選択**: 自分×相手の方針の行列（最大打点・毎ターン最善手・準備の手（積み技の数）・持久戦）で、各側が相手の最善の応手を前提に最も有利な方針を選ぶ
  （自分は max-min、相手は min-max。同点は候補の順＝最大打点→毎ターン最善手→準備の手→持久戦）。選んだ組の対戦結果が判定。
- **出力**: `myPlan/oppPlan`（`max`/`seq`/`prep`/`stall`）、`myPrep/oppPrep`（準備の技名。無ければ null）、
  `mySeq/oppSeq`（判定の対戦で実際に撃った技の並び。準備の技を使うときは先頭。同じ技の連打なら空）。
  準備の手・持久戦を選んだ側は、`a`/`b` の `seq`・`seqHits` も判定の対戦の値に置き換える。
  `verdict.stall` は常に `{side: null}`、`verdict.plans` は `{me: null, opp: null}`（旧・持久戦ルートの表示の互換。持久戦は myPlan=`stall` と race で表す）。
- **経過（ダメージレース）**: 選んだ組の実際の対戦を `verdict.race`（行動ごと・ターン終了時ごと。`turn/actor/move/flinch/hp[a,b]/events[{side,kind,amount}]`、
  amount は正=ダメージ・負=回復）で返す。原因は対戦本体が発生した場所で記録する（`battle.rs` の `RACE_CAUSES`/`race_cause`。
  純増減からの推定はしない＝天候とたべのこしの相殺・はたきおとすで落ちたきのみを「食べた」扱い等の取り違えが起きない）。
  kind は move（技・原因不明の残り）/ recoil / lifeorb / helmet / roughskin / drain / liquidooze / shellbell / berry / weather / status /
  grassy / leftovers / sludge / heal / sandstorm / poison / badpoison / burn / bind（まとわりつく等の拘束）/ leechseed（やどりぎのタネ。吸った側は回復）/
  saltcure（しおづけ）/ curse（のろい）/ eot（ターン終了時のその他）/ other（行動側のその他）/ disguise。攻撃技を持たず何もしなかった行動は行にしない。
  再生のメッセージは原因名を出す（bind は縛った技名で「まとわりつくで 21ダメージ」、もうどくは「もうどくで 10ダメージ」）。
  `raceInit.events` は開始局面を作るときの入場効果・メガシンカで発動した特性の記録（実際の発動順。`phase`=entry/mega・`side`・`ability`・
  `abilities`（両者の特性）・`weather`/`terrain`（変わったときの新しい値）・`wx0`（直前の天候）・`stg`（両者の能力ランクの変化）・`effect`（場やランクが変わったか））。
  再生は開始画面（メガシンカ前の状態に戻して表示）に入場時の発動、1ターン目の先頭にメガシンカとメガ後の特性の発動を出す
  （「ボーマンダの いかく！ ズルズキンの 攻撃が 下がった！」「メガリザードンYの ひでり！ 日差しが 強くなった！」。相手の まけんき・かちき は
  相手の特性として分けて「エンペルトの かちき！ 特攻が ぐーんと上がった！」）。判定は変えない（開始局面の作り置きに一緒に持つだけ）。
  `raceInit.mega` は各側のメガシンカ情報 `{from, to, ability, stone}`（しなければ null）。再生は開始画面をメガシンカ前の名前と「メガシンカする」、
  1ターン目の行動前に「XはメガXにメガシンカした！」（先に動く側から）、以降はメガの名前・特性とメガのバッジで表示する（メガの画像素材が無いため絵は通常の姿）。
  並びは左＝自分・右＝相手で、開始メッセージの順と揃える。「最初から／前／次」を押したら、操作ボタン〜そのターンのメッセージ末尾が画面（ダイアログ内ならその
  スクロール領域）に収まるよう自動でスクロールし、収まらなければ操作ボタンを上端に合わせる。へんげんじざい/リベロの先回りの型変化は、
  判定の対戦の1ターン目に実際に先に動いたとき（優先度込み）だけ適用する。同速で `tie` のときの `myS/oppS` は同速だったターンの素早さ。
  とどめの一撃で残りHPより大きい技のダメージは、move イベントに `raw`（残りHPで頭打ちにする前の技のダメージ。連続技は合計、きあいのタスキ・がんじょうで耐えた場合は耐えた後の値、
  みがわりへのダメージは含めない）を付ける。`amount`（実際に減ったHP）とHPバー・棒は従来どおりで、再生のメッセージだけ `raw` と最大HP比の%（100%超えも可）を出す
  （`battle.rs` が `race_cause(…, "rawmove", …)` で記録し、`race_entries` が原因の合計から外して raw に付ける）。
  ばけのかわが剥がれた行動は、技のダメージを0（`blocked: "ばけのかわ"`）とし、剥がれたときの最大HP1/8を `disguise` として分ける（表示「じしん → ばけのかわで無効」「ばけのかわが剥がれた（1/8）」）。
  毎ターンの行は `dealt`（判定の対戦で実際に減らしたHP）を持ち、ダメージレースの棒の長さはこれと反動等の実際の量で描く（倒れた側の棒は右端まで埋まる）。
  棒のセグメントは button で、タップ/クリックでターン番号・技名/原因・実際に減ったHPと%・技の幅を表示する（mu-card は `bindMuCardClicks`）。
  量は実際のHPの増減から出し、内訳の合計は必ず増減と一致する（`battle.rs` の `RACE_LOG` は判定時だけ有効な記録で、対戦の挙動は変えない）。
  `a`/`b` の `turns` は全対面でこの経過から作る（実際に動いたターンだけ。倒れた後の行動は無い。`flinch`＝ひるんで動けず、
  `extra`＝そのターンに相手が技以外で減らしたHP（原因の行動の `turn/late` つき）、`heal`＝相手の回復、`turn`＝ターン番号、`late`＝そのターンに後から動いた）。
  工房のダメージレースの棒・1v1の毎ターン表示はこれを描き、後から動いた行動と、それが起こした反動等は「1'」のようにダッシュを付ける。ひるんだターンは番号を出さない。
  自分が先に倒されて動けなかったターンでも、相手がそのターンの行動で反動等によりHPを減らしていれば `idle: true` の行としてHPの変化だけ残す（決着の行動に伴う反動・いのちのたま・ゴツゴツメット・きのみ等を落とさない）。
- **入力の検査**: 未知の種族・読めない努力値の spec は組み立て前にエラーを返す（`poke::spec_error`。wasm は -2 と `{"error"}`、
  pyengine は ValueError）。pyengine は判定中のパニックも捕まえてエラーにし、ロックが壊れても（poison）次の呼び出しで回復して scenario を既定に戻す
  （提案APIが1件の不正な入力で止まらないように）。
- **判定の説明の「撃つ技」**: 工房・相性表の説明で使う技は判定の対戦で選んだ `myMove/oppMove`（技ごとの一覧の `best` は元のタイプで計算した最大打点で、
  へんげんじざい等で違うことがある）。
- **技ごとの前提の注記（`conds`、`relevant_conds`）**: 天候・フィールド・攻撃側の攻撃/特攻ランクは、その技のダメージを実際に変えるものだけを出す。
  判定はダメージ計算そのもの（`calc_damage`、最高乱数・急所なし）に、その条件を外した場合と比べさせる（表示用の規則表は持たない）。
  例: 特殊技の あくのはどう に「攻撃-1」は付かない／ボディプレス・イカサマに攻撃ランクは付かない／じめん技にエレキフィールドは付かない／
  すなあらしは防御側がいわタイプで特殊技のときだけ付く／無効（ダメージ0）の技には付けない。
  防御側の特性による補正も同じ方式で付ける（特性を外すとダメージが変わるときだけ。`防御特性:マルチスケイル` の形で返し、表示は「相手のマルチスケイル（HP満タン時）」。
  マルチスケイル・ファントムガードは満タン時の前提を添える）。フィルター・ハードロック・あついしぼう・ファーコート・はどうのぼうご 等も自然に拾う。
  かたやぶり等で無視される場合は付かない。攻撃側の特性（スカイスキン等）は対象外。ばけのかわは従来どおり別扱い。連続技の回数の前提（「3ヒット時」等）は従来どおり。
- **表示用の値は従来どおり**: 各技の `hitsLo/hitsHi/dmgLo/dmgHi/conds`・`ko_probability` は相手を棒立ちにした実走のまま。
  技ごとに `eff`（タイプ相性の倍率。特性・ふうせんによる無効は0）を返す。技ごとのダメージ一覧（`a/b.moves`）は、防御側が
  へんげんじざい/リベロ でタイプを変える前の**元のタイプ**で計算する（型の変化は判定・経過・再生だけに反映。以前の `defForm` と
  「〜タイプになった後」の注記は廃止）。判定（記号・経過）は従来どおり型の変化を先回りした計算のまま。
- 計算量: サイトの全種×上位30×3型×3型の一括判定（TS側のキャッシュ込み）で、1方式(最低乱数)0.35ms→方針の組の2者対戦0.62ms→乱数3点1.11ms/対面。
  2026-09-27: 持久戦の方針・倒れたターンの終了時処理で1.6ms→中央乱数1点で0.86ms→次の高速化で0.40ms（結果は全対面で出力JSONまで完全一致）。
  (1) 方針の組の対戦で、局面は「同速時の先後・仮定の続きか・それまでの両者の行動列」で一意に決まるので、各局面の方針の手と best_attack を
  使い回す（`SimMemo`）。毎ターンの局面の写しは経過の表示時だけ取り、決着したターンは行動列から再生して作る。
  (2) 分析の局面は相手の見え方（opp_view）を更新しない（`Field.no_view`。AI・信念を使わないので結果は不変）。
  (3) 開始局面を対面・乱数・前提ごとに作り置き、複製して使う。暴れ技を持たない側は「暴れ技を避ける手順」を別に回さない。
  最低乱数で1発の技は中央・最高乱数でも1発なので回さない。(4) wasm を opt-level 3 でビルド（"z" の約2倍速、gzip 192KB→243KB）。

**天候の防御補正の適用順序**：砂の「いわ特防×1.5」・雪の「こおり防御×1.5」は、

（これらが無視するのは**ランク変化であって天候補正ではない**）。
判定は「B参照技かD参照技か」で行い、B参照技には雪の補正のみ・D参照技には砂の補正のみが乗る。

### 4-4. HP計算式

```

```

### 4-5. ステータス計算式

```

```

### 4-5b. 瀕死交代先の選択（AI）

繰り出し先は**2層**で決める（控えが1匹なら自明・2匹以上の時のみ選択）：
- **実戦の根の決定**：`SearchAI.choose_faint_switch` ＝「交代のみを候補にした通常の価値ベース選択」。各控えを『繰り出し→相手最善応手（K型サンプルの最悪）』で価値ネット評価し最良を選ぶ。反撃KO・受け回し等は価値ネットで一元評価され、個別ルール不要。`Battle.run` が各サイドのAIから取得して使用。
- **シミュ内のロールアウト方策＋フォールバック**：`_best_faint_switch`（高速ヒューリスティック）。タイプ相性に加え**反撃KO**（控えが相手より速く、最大打点で相手の現在HPを削り切れる）を最優先。速さはこだわりスカーフ・まひ・天候特性（すいすい等）を加味。MCTSの各シミュ内faintはこちらを使う（フル探索の再帰を避けるため）。

### 4-6. 行動順と瀕死交代のタイミング

1ターン内で両者は素早さ順に行動する。**ターン中に瀕死になったポケモンの交代（瀕死交代）は、両者の行動が終わったターン終了時に行う**（残ダメージ処理の後）。

- **先攻が自滅した場合**（反動技＝はめつのひかり/すてみタックル/フレアドライブ等の反動、または だいばくはつ/じばく の自爆）、その場は空になる。**後攻の技は対象不在で失敗**し、交代先はそのターンは攻撃を受けない。交代先はターン終了時に着地する（このターンの残ダメージも受けない）。
- **ピボット技（とんぼがえり/ボルトチェンジ/バトンタッチ等）は瀕死ではない自発交代**なので、交代先は通常どおりその場に出て後攻の攻撃を受ける（自滅瀕死と区別する）。
- 実装: `_do_action(defer_self_faint=True)` で先攻の自滅瀕死交代を保留し、後攻は対象不在を検出して失敗。保留分は `_end_of_turn` 末尾の `_faint_switch` が回収する。

## 4. 情報開示（情報の非対称性）

AI同士の対戦学習を見据え、各サイドが相手について「何を知っているか」を `OpponentView`（`opponent_view.py`）で管理する。各 `BattleSide` は `opp_view`（＝そのサイドが相手パーティについて持つ知識）を保持する。

### 4-1. 開示のタイミング
1. **対戦前の見せ合い**: バトル開始時、両者は相手の**候補6体の種族・タイプ**を知る（`team_preview`）。この時点で技・持ち物・特性・努力値は**未開示**。`PokeKnowledge.previewed = True`。
2. **登場時**: 場に出たポケモンを確認（`on_enter`、`seen = True`）。**先発もバトル開始時（`Battle.run` の見せ合い直後）に `on_enter` する**。交代時にしか記録していなかった頃は先発が `seen=False` のまま残り、先発が一度引っ込むと探索の隠れ選出（`_resample_hidden_bench`）が先発の枠を別個体に引き直していた（技は見えているのに正体が差し替わる。Rust `Battle::start` も同じ）。あわせて、**実機で登場した瞬間にメッセージが出る特性・持ち物**をここで確定させる（`ENTRY_VISIBLE_ABILITIES` / `ENTRY_VISIBLE_ITEMS`）。
   - 特性: いかく・天候設置4（すなおこし/ひでり/あめふらし/ゆきふらし）・フィールド設置3（エレキ/グラス/サイコメイカー）・ダウンロード・トレース・かんろなミツ・かわりもの・プレッシャー
   - 持ち物: **ふうせん**（「浮いている」と表示される）
   - ここに **殴って初めて分かるもの（ゴツゴツメット・きあいのタスキ・いのちのたま等）を入れてはならない**＝リークになる。逆に入れ忘れると、AIが登場時に分かるはずの情報を知らずに戦う。
3. **発動・使用ベースの開示**: 以降は実際に観測された情報のみが開示される。
   - **接触技を当てた時**: 防御側の ゴツゴツメット / さめはだ / てつのとげ が攻撃側に開示（`_disclose_contact_reaction`）。発動条件は `_rough_skin_recoil` と一致させる（えんかく・かたやぶり系の除外を含む）。
   - **ばけのかわが破れた時**: 特性を開示。**ふうせんが割れた時**: 持ち物を開示。
   - **メガ進化した時**: 形態が見えるのでメガ石と進化後の特性を開示。
   - 技を使う → `on_move`（`known_moves` に追加）
   - **持ち物が消費・はたき落としで無くなったことも公開情報**（実機では何を失ったかまで表示される）。`Battle._sync_item_loss` が各ターンの行動選択の直前に、前回から持ち物が無くなった個体を相手の `opp_view.on_item_lost` に記録する（`item_lost=True`・`known_item` も確定）。開示していたのはタスキ・ふうせん等の一部だけで、きのみを食べた相手も含めて決定化（`SearchAI._sample_opp_config`）が持ち物を戻していた（タスキを使い切った相手を探索の中で再びタスキ持ちとして読んでいた）。決定化は `item_lost` の相手に持ち物を付けない。スナップショットは Battle ごとに持つので、探索の1手ごとの Battle では記録しない（Rust `sync_item_loss`・`sample_opp_config` も同じ。`ITEM_GONE=0` は A/B 用の旧挙動）
   - 持ち物が発動/判明（オボン回復・タスキ・はたきおとす等）→ `on_item`（`known_item`）
   - 特性が発動（がんじょう・いのちのたま反動等）→ `on_ability`（`known_ability`）
   - ダメージを受ける → `on_hp_change`：相手HPの**残り割合**（`hp_fraction`、実数HP/最大HPは不可視。HPバーから観測できる割合のみ）と、**その技で減った割合**（`damage_log` に `{move, attacker, fraction}` を追記）を記録。主にダメージ割合からダメージ計算を逆算し、相手の努力値・性格を類推する用途。

### 4-0b. はたきおとす の威力補正（メガストーン除外）

はたきおとすは相手が持ち物を持っていると威力1.5倍だが、**メガストーンは叩き落とせないので
対象外**。判定は接尾辞で行う: `ナイト` / `ナイトX` / `ナイトY` / `ナイトZ`（全角 `ナイトＸ/Ｙ/Ｚ` も）。
M-6 で追加された **Zメガ石（ナイトZ）** は Rust 側の判定から漏れており、同じ盤面で
Python 81 / Rust 120 と 1.5倍ぶん食い違っていた（マスカーニャ→アブソル@アブソルナイトZ）。
勝敗まで変わるため fresh_parity で 1/200 の乖離として表面化した。接尾辞を増やすときは
`damage.py` と `damage.rs` の両方を必ず揃えること。

### 4-1c. 信念の観測チャネル（`belief.py` / `belief.rs`）

相手の型（EV・性格・持ち物）は `OpponentBelief` が **種名をキー**に持つ。場のポケモンではなく
種ごとなので**交代しても残る**。`ensure()` は遅延生成で、場に出るまで信念を作らない。
`__deepcopy__` は `None` を返す＝MCTSの決定化ロールアウトには持ち込まない（信念は対戦状態では
なく意思決定者の知識で、探索中の出来事で実信念を汚染してはいけない）。

観測は「実機で見える情報」だけを使う。4チャネルある:

| チャネル | 何から | 何を絞る |
|---|---|---|
| `observe_damage` | 自分が与えたダメージ割合 | 相手の**耐久**（H/B/D） |
| `observe_damage_dealt` | 自分が受けたダメージ割合 | 相手の**攻撃**（A/C） |
| `observe_order` | どちらが先に動いたか | 相手の**実効速度**、こだわりスカーフ |
| `observe_absent_item` | 発動しなかったこと | 持ち物の**否定** |

- `observe_order` は**優先度が同じ技同士のときだけ**呼ぶ（違えば速度の情報にならない）。交代は
  速度と無関係なので対象外。候補ごとに「持ち物なし」と「こだわりスカーフ(×1.5)」の両方を試し、
  **スカーフでしか説明できなければ確定**させる。遅かっただけではスカーフを否定しない（下振れがあるため）。
  速度倍率は `battle._speed_order` / `ai._effective_speed` に揃えること。
- `observe_absent_item` は HP が満タンでないときだけ呼ぶ（満タンでは回復が起きなくても何も分からない）。
- 開示済み（`known_item`）があればそちらが優先で、否定的観測は何もしない。

実測（自己対戦40戦・真の型と突き合わせ）: スカーフ検出 6/45 → 25/45、
持ち物の平均確率 43.8% → 50.0%、EV配分のMAP一致 65.1% → 73.3%。

既知の制約: 候補の実体は `ensure()` 時点の開示情報で1度だけ構築するため、**スカーフ確定後も
候補を作り直さない**（耐久・速度の推定をさらに締められる余地）。同じ種が2体いると種名キーが
衝突して信念が混ざる。

### 4-1b. AIが読んでよい情報（リーク禁止）

対戦AIは **`opp_view` の開示済み情報**と、**見せ合いで分かる種族からの使用率事前分布**の2つ以外を読んではならない。
相手オブジェクトの真値（`opp.item` / `opp.ability` / `opp.moves`）を直接読むと、人間が「タスキかもしれない」と
迷う場面で迷わないAIになり、勝率もブランダー率も実力より良く出る。

`certain_ko_override`（`ai.py`、本番MCTS/ネットの出力に被せる確定KO安全弁）での扱い:
- **耐える系の判定**（`_survives_unknown`）: きあいのタスキ／マルチスケイル／ファントムガード／がんじょう。
  開示済みならそれを使う。未開示なら使用率事前分布で判断し、**特性は90%以上で確定扱い**
  （見せ合いで種族が公開されるため。ミミッキュ=ばけのかわ100%等）、**きあいのタスキは採用率10%以上なら
  「耐えるかもしれない」側に倒す**。M-6 実測では最頻特性が90%未満＝特性が読めない種が 200種中56種(28%)あり、
  「特性は種族で決まるから真値を読んでよい」は成り立たない（例: ブリジュラスの がんじょう 26%）。
- **ばけのかわ未破壊の判定**（`_disguise_intact`）: 破れたかどうかは実機で見える。特性自体は事前分布で確定扱い。
- **先制判定**（`_goes_first(..., my_side)`）: 相手の最大優先度は、開示済みの技と**使用率50%以上の技**だけから推定する。
- **成功条件のある技は、条件を満たさない局面では確定KOの候補にしない**（`_ko_move_fails`／Rust `ko_move_fails`。2026-10-04）:
  ねこだまし・であいがしら（場に出て2ターン目以降＝`turns_out>0`）、ポルターガイスト（相手の持ち物なし）、とっておき（他の技を使い切っていない）、
  アイアンローラー（フィールドなし）、サイコフィールド中に接地した相手への先制技。ふいうち・はやてがえし（相手の行動しだい）と
  みらいよち（威力が後で入る）は常に除く。以前は2ターン目以降の であいがしら を「先制で確定KO」として探索の手を上書きし、毎ターン失敗していた
  （メガグソクムシャ: 60戦で失敗35回）。env `AI_KO_COND=0`（側2だけは `AI_KO_COND_2=0`）で旧判定（A/B 用）。
- **命中率とタイプの条件**（2026-10-04・監査40 #3）: 候補は命中率（技の命中・命中/回避ランク・天候（雨のかみなり/ぼうふう・雪のふぶき＝必中、晴れのかみなり50%）・
  ノーガード・ロックオン・ふくがん・はりきり・こうかくレンズ・ひかりのこな。`_ko_hit_prob`／Rust `ko_hit_prob`）の高い順、同じなら最低ロールのダメージの大きい順。
  **命中が確実（1.0）でない技で上書きするのは、探索の選んだ手がそれより命中率の低い確定KO技だったときだけ**（10まんボルト で倒せるのに でんじほう に替えない／
  探索が選んだ別の手を命中50の一撃で上書きしない）。でんきタイプを失った でんこうそうげき・ほのおタイプを失った もえつきる は候補にしない。
  env `AI_FIX40=0`（Rust は側2だけ `AI_FIX40_2=0`）で旧判定。
- **見積もりで状態を変えない**（2026-10-04）: `calc_damage` は実際の攻撃のために半減きのみの消費（＋かるわざ）・じゅうでん/でんきエンジンの解除を行う。
  確定KOの判定と瀕死交代の反撃KO判定（`_best_faint_switch`）は対戦中の実体で見積もるので、`damage.estimate_only`（Rust `damage::EstSnap`）で
  その状態を見積もりの後に戻す。以前は確定KOの判定だけで相手のシュカのみ等が消え、実際の攻撃が半減されなかった（Python/Rust の再生の食い違い3件の原因）。
  選出・価値ネットの特徴量は写しの上で計算し、消費の順序まで含めて学習済みなので変えない。
- **信念の観測再計算でも状態を変えない**（2026-10-04 監査200 R4-mcts 照合）: ダメージ観測から型の重みを絞る再計算
  （`belief.observe_damage` / `observe_damage_dealt` / `pool_weights` / `_apply_choice`、Rust 同名）は候補・ロールごとに
  `estimate_only`／`EstSnap` で包む。以前は観測の写しの充電（でんきにかえる・じゅうでん）や半減きのみが1回目の計算で消え、
  Python は2候補目以降を、Rust は2プロファイル目以降を充電なしで計算していた（型の重みが Py/Rust でずれ、R4-mcts の乖離 6/294 の原因）。
- **メガ前提の候補の技タイプ**（2026-10-04 R4-mcts 照合）: タイプ無効の技の候補除外（`_type_immune_move`／Rust `type_immune_move`）はメガ進化つきの手ではメガ後の特性で技タイプを決める。Rust の `effective_move_type_ab` は ウェザーボール の天候だけメガ前の特性で見ていた（メガニウム→メガソーラー の ウェザーボール+メガ を ゴースト相手に「ノーマルで無効」として外していた）のを Python と同じにした。

`opp_view` が無い経路（単体テスト・素の `BattleSide`）は従来どおり真値にフォールバックしてよい。
`HeuristicAI` 内の `_opp_priority_threatens` / `_wall_break_action` / `_is_likely_threatened` は
真値を読む（docstringに「メタ知識」と明記）が、本番の決定経路には乗らない。

### 4-1e. AIの型の読みのスナップショット（2026-09-28）

`simulator/predict.py`（Rust `predict.rs`）の `Predictor.snapshot(side, opp_side)` は、読む側 side のAIが
相手の各ポケモン（opp_view に載っている種）をどう読んでいるかを JSON で返す。対戦記録・再生・精度集計用。
- **信念を書き換えない**（写しの上で計算する）。記録を付けても対戦の進行・乱数・AIの判断は変わらない。
- 項目: `appeared`（場に出たことがある）/ `known`（判明した技・持ち物・特性・持ち物喪失。信念と opp_view の和）/
  `marginal`（使用率ベース＝JOINT_BUILD=0・型が無い種の決定化が引く分布: 技ごとの所持確率＝使用率/100・判明技は1.0、
  持ち物・特性の確率、努力値/性格の事後上位3）/ `pool`（型プールの事後＝既定の決定化が引く分布:
  判明情報と矛盾しない型の数、上位5型〔系統 phys/spec/mix・確率・持ち物・性格・努力値・特性・技〕、型の事後から出した
  技/持ち物/努力値性格の確率。型が無い種・矛盾しない型が無いときは null）/ `used`（その時点でAIが実際に使う方）。
- 確率の並びは小数4桁に丸めた値の降順・同率は名前順（浮動小数の和の順序差で並びが揺れないように）。
- 型の系統（`side`）は datapack の `build_pool` に載せた（`datapack_export.py`。決定化には使わない）。
- 記録: `feature1.play_and_record(..., predict=True)` で `turns[i].predict = {"side1": 読み, "side2": 読み}`
  （ターン i の処理後＝次のターン開始時）と `truth`（選出個体の実際の型）を足す。既定は False で従来の記録と同じ。
- Python↔Rust 一致: `_rust_engine/predict_parity.py`（greedy 対戦で両側の信念を持たせ、全ターンの読みを照合。
  2026-09-28: JOINT_BUILD=0/1 とも 40/40・276ターン）。Rust は `PREDICT_PROBE=1`（`BELIEF_PROBE=1` と併用）で
  各ターンの読みを控え、`pokenavi_engine.predict_probe_take()` で取り出す。
- 付随して直した不一致: Rust `battle::is_megastone` が Zメガ石（〜ナイトZ/Ｚ）を含んでいなかった
  （Python `_is_megastone` は含む）。ガブリアスナイトZ 等を はたきおとす/トリック で奪えてしまい、JOINT_BUILD=1 の
  型の読みでもメガ後の特性で型を全部弾いて周辺分布に落ちていた。

### 4-1g. 相性ベースの規則的な選出（SELECT_MODE=matchup、2026-09-29）

`simulator/selection_matchup.py`。ニューラル選出（selector_*）のベースラインで、`learned_select_party` が env `SELECT_MODE=matchup`
のとき委譲する。考え方: 相手6体のうちどの3体が来ても穴が無い3体を選ぶ。
- 相手が来うる3体（メガ1体ルール。相手のメガ石の有無は型プールの最多の型の持ち物で見る）ごとに次の重み付き和を計算し、
  平均と最悪の混合（alpha）が最大の自分の3体（メガ1体ルール）を選ぶ:
  攻め（相手の各ポケモンに自分の3体の技で通る最大の相性）− 守り（相手が持っていそうな攻撃技のタイプ＝型プールの型の重みで、
  そのタイプに抜群を取られる自分のポケモンが2体以上なら (数−1)×確率）＋ 1v1（Rust の1v1エンジンで勝てるか。相手は型プールの
  最多の型）＋ 負荷分散（相手の各ポケモンに勝てる自分のポケモンの数、2体で満点）。
- 先頭は相手6体への1v1の勝ち数（同数は攻めの通り）で決める。
- 相手の技・持ち物の真値は読まない（種族→型プール。相手のタイプは見せ合いで分かる素のタイプ）。
- 重みは env `SELECT_MU_W="off,dfp,mu,load,alpha"`（既定 1,1,1,1,0.5）。テスト: test_all 26j。
- メガ1体ルールで「ちょうど1体」の組が作れないとき（相手の推定メガ石持ちが5体以上など）は、メガ石持ちの数が最少の組で代える
  （`_trios`。以前は候補が空になり例外になっていた。2026-09-30）。

### 4-1c. 探索AIの根の候補から無効技を外す（2026-09-28）

`SearchAI.__call__`（Rust `SearchAI::choose`）は、根の候補から**相手の場のポケモンにタイプで無効な攻撃技**を外す
（`search_ai._prune_immune_moves` / Rust `search::prune_immune_moves`）。env `AI_PRUNE_IMMUNE=0` で旧挙動（A/B用。
Rust は `AI_PRUNE_IMMUNE_2` で側2だけ変えられる）。
- 判定は対戦本体 `execute_move` のタイプ無効と同じ（実効タイプ `_effective_move_type`＋きもったま）。
  **メガ進化と同時に撃つ技はメガ後の特性**で実効タイプを決める（メガボーマンダのスカイスキン すてみタックルはゴーストに当たる）。
- 相手の特性による無効（ふゆう・もらいび・ちょすい等）は非公開情報なので見ない（4-1b）。
- **他に技の候補が無いときは外さない**（こだわり固定で残る技が無効技だけ等）。居座りか交代かは探索に任せる
  （瀕死級を居座らせて倒させ、後続を無償で出す判断があり得るため）。
- 外すのは根だけ。木の中（相手の手・2手目以降）の候補は従来どおり。
- 根拠（本番ネット同士300戦・Python MCTS@400）: 無効技は手番の0.7%。強制プレイアウト（その手を指した後を
  本番AI同士で最後まで対戦）では、外して残りの手に振り替えても勝率差 +0.1pt±0.3 ＝**強さは変わらず見た目の悪手だけ消える**。
  無効技は勝敗がほぼ決まった局面（どの手でも勝率0や1）で、Q値が同値タイになり方策priorに引かれて選ばれていた。

**必ず失敗する手・効果の無い手も根から外す**（2026-10-04・監査40 #18〜#20。`search_ai._prune_futile_moves`／Rust `search::prune_futile_moves`。
env `AI_FIX40=0`／Rust 側2 `AI_FIX40_2=0` で旧挙動）。判定は公開情報だけ（`_futile_move`）:

  すでに状態異常・しんぴのまもり・タイプ（でんき→まひ・じめん→でんじは・ほのお→やけど・どく/はがね→どく（ふしょく以外）・くさ→粉）で入らない状態異常技、
  ねむけ中の相手への あくび、ちょうはつ中の相手への ちょうはつ、アンコール中・まだ技を使っていない相手への アンコール、やどりぎ中・くさタイプへの やどりぎのタネ、

- 開示済みの持ち物・特性で無効な攻撃技: 登場時に見えた ふうせん の相手への じめん技、判明した特性（ふゆう・ちょすい 等）で無効な技（かたやぶり系は除く）。

## 5. 戦略学習環境（自己対戦）

登録済みパーティ同士のAI自己対戦を多数繰り返し、最も勝率の高い戦略を学習させるための環境。アプローチは**探索＋ゲーム理論**（決定化MCTS／expectimax で行動方策、ナッシュ均衡で選出方策）。

### 5-1. 学習対象
1. **選出方策**: 相手の候補6体から、自分の6体のうちどの3体を選び、どれをリード（先頭）にするか（`SelectionPolicy`）。
2. **行動方策**: 毎ターンの行動（技/交代/メガ）。開示情報＋非開示情報の推定（belief）を用い、勝率を最大化する行動を選ぶ。

### 5-2. 環境ハーネス（`env.py`） ※Phase 0実装済み
- **登録テンプレート（正本）**: DB表 `templates` が唯一の正本（M-1上位の情報完全な73構築、`party_id`=順位、型・EV・性格・技確定）。`load_templates`/`load_registered_parties` で読み込み、`build_party`（randomize=False）で確定スペック構築。`build_templates.py` が正本を構築、`generate_ui_templates.py` がUI用の派生一覧（上位100）を生成。旧 `m1_party` 表／`gamewith_parties.json`／手書き `party_templates_new.txt` は本表に一本化し廃止（txtはDB生成物）。データ源は GameWith「上位構築」のため上限は約95件（完全73件）で、ランキング1〜1000位の個人チームは非公開のため取得不可。
- **完全性保証**: `is_complete_party`（種族・技がDB解決可・『不明』なし）で検証。全テンプレートが完全であることを `test_all.py` で固定（誤記・欠落の回帰検出。例: 過去に「エンベルト」=エンペルトの誤記を検出・修正）。
- **選出方策インターフェース**: `SelectionPolicy = (my6, opp6, loader) → 順序付き選出リスト`（先頭=リード）。既定は現行ヒューリスティック（`heuristic_selection`）。学習方策に差し替え可能。
- **対戦実行**: `play_match(p1, p2, loader, ai1, ai2, sel1, sel2)`。行動方策(ai)も差し替え可能。
- **状態クローン／継続**: `Battle.clone()`（deepcopyで独立複製）と `Battle.resume(ai1, ai2)`（見せ合い・初手入場を再実行せず途中状態から継続）。決定化ロールアウトの土台。
- 速度: 単一プロセスで約360試合/秒（10万試合≈5分）。

### 5-3. 推定器（`belief.py`） ※Phase 1実装済み

非開示情報を確率分布として推定する。`PokemonBelief`（相手1体）と `OpponentBelief`（サイド全体＝種族名→PokemonBelief）。

- **技/持ち物/特性**: 使用率DB（`top_moves`/`top_items`/`top_abilities`）を事前分布とし、`opp_view` の開示（`observe_disclosure`）で確定。ダメージ計算は使わない（ユーザー要件「使用率や組み合わせから確率的に警戒」）。`prob_has_move`/`prob_item`/`prob_ability` で参照。
- **EV/性格**: 使用率の `top_evs × top_natures` を候補スプレッドとして列挙（各候補は具体的な防御体を構築）。`observe_damage` で、攻撃側を既知としてダメージ式を逆算し、16段階の乱数ロールで観測割合を再現できる割合を尤度としてベイズ更新。再現不可な観測（マルチヒット・急所等のモデル外）は安全にスキップ。`map_spread`/`spread_posterior`/`expected_stat` で参照。
- **登録スプレッド混入（発展②）**: `OpponentBelief(use_registered=True, 既定)` は `m1_party` の実スプレッド（種族別）を候補に追加する（`registered_spreads_by_species`、キャッシュ付）。このメタは登録パーティ同士のため真の型が候補に入り、ダメージ観測で尤度が集中する。耐久(防御/特防)推定の事後誤差が事前比 約65%改善（混入なしは約10%）。
- **統合**: `BattleSide.belief`（任意）に `OpponentBelief` を付与すると、被ダメージ確定点（`on_hp_change` と同じ箇所）で自動的に `observe_damage` が呼ばれEV/性格を推定。`belief` は対戦状態ではなく意思決定者の知識のため `Battle.clone()`（ロールアウト）には引き継がれない（`__deepcopy__`→None）。
- **参照シーズン（`BELIEF_SEASON`）**: 事前分布を引くシーズン。既定は env `BELIEF_SEASON`、未設定なら `"M-2"`。明示引数 `OpponentBelief(loader, season)` は env より優先。
- **欠損時フォールバック（型リーク防止・2026-09-14）**: 指定シーズンに使用率行が無い種は、行のある最新シーズンへ自動フォールバックする（`_tpl_with_prior`。Rust `belief.rs` も同一）。事前分布を空のままにすると `_determinize` が falsy を上書きしない実装のせいで**相手の真の持ち物・特性・技が探索に残る＝型リーク**になるため、空の事前分布は許さない。`test_all.py` 節26 が M-6 上位40種で不変条件を検査する。
  - シーズンが実環境とずれると、そのシーズンに使用率行が無い種は**事前分布が丸ごと空**になる（`top_moves`/`top_items`/`top_abilities` が空 → 技prior 0・持ち物0・特性0、EV/性格候補は「無振り・まじめ」1件のみ）。M-6 の200種のうち53種、上位40種のうち14種（ボーマンダ・グソクムシャ・セグレイブ・サーフゴー等）が M-2 に存在しない。
  - 影響は決定化に出る。ただし内訳は一様ではない（2026-09-14 実測）:
    - `_determinize` は `item`/`ability`/`moves` を falsy なら上書きしない（`if c.get("item") is not None:` 等）。事前分布が空だと相手の**真の持ち物・特性・技がそのまま残る**＝探索にとってはむしろ有利な情報漏れになる。
    - 一方 EV/性格は**常に上書き**されるので、事前分布が空の種は必ず「無振り/まじめ」になる（過小評価）。
    - `_resample_hidden_bench` は `self.season` のテンプレで控えを作り直すため、使用率行の無い種は**技0本・特性''・持ち物None** の個体が木に入っていた。上振れ要素のない純粋な誤りなので `_tpl_playable()`（使用率行のあるシーズンへフォールバック）で修正済み。Rust（`TplCache::get_playable`・技0本の個体は差し替えない）も 2026-10-04 に同じにした（監査200 R4-mcts 照合。以前は Rust だけ ケンタロス:水 等を M-6 の空テンプレで作り、乱数の消費がずれていた）。
  - **Rust は `sim.rs` の `BELIEF_SEASON="M-2"` 定数を使う**ため、`BELIEF_SEASON` が M-2 以外のときは `engine_dispatch` のガードで Python 経路に落ちる（パリティ保護）。Rust 側を引数化するまではこの制約が残る。
- 既知の制約: 候補防御体は `ensure()` 時点の開示特性/持ち物で1度だけ構築（途中の持ち物判明では再構築しない）。急所観測は非急所モデルと一致せずスキップ。
- 検証: 自己対戦では相手の真の型を我々が知っているため、`map_spread` の的中・事後>事前を直接テストで検証（`test_all.py` 推定器節）。

### 5-4. 行動方策（`search_ai.py`） ※Phase 2実装済み

`SearchAI`：毎ターン、belief から相手の非開示情報（EV/性格・持ち物・特性・未開示技）を K 通りサンプリングして相手を具体化（決定化）し、各候補行動について `Battle.clone()`＋`resume(max_turns=depth)` で短いロールアウトを回して勝率を見積もり、勝率最大（＝負ける確率最小）の行動を選ぶ。

- 観測可能な状態（現在HP割合・ランク変化・状態異常・場・メガ）はクローン元から保持し、非開示情報のみ belief から差し替える。メガ/へんしん中の個体はステータスを再サンプルしない。
- K個の決定化世界を全候補で共通利用（common random numbers）して候補間分散を抑える。ロールアウトの行動は高速な `rollout_ai`（既定 HeuristicAI）。テンプレート未登録種は決定化をスキップ。
- 既定 `rollouts=16, depth=50`。評価：HeuristicAI に対し約77%勝率（登録スプレッドbelief併用時。深さ・Kを上げると向上）。1試合あたり約0.7秒。
- **メガ進化の探索**: メガ可能時は「メガする／しない」を**独立した候補**として勝率比較する（旧実装は `should_mega_evolve` の判断を一律付与するだけだった）。`should_mega_evolve` は「石があれば原則即メガ」に修正（旧実装はメガ種族値÷現行実数値のスケール不一致で発動タイミングが偶然任せ・ハッサム等の物理メガが満タンで発動しないバグがあった）。メガ石名の全角Ｘ/Ｙと半角X/Yの不一致も `normalize_mega_stone` で吸収し、リザードンX/Y等が正しくメガ可能に。
- **再帰探索（発展③, opt-in）**: `make_nested_search` は外側 SearchAI のロールアウト方策に予算を絞った内側 SearchAI を用いる2段ネスト（内側のロールアウトは HeuristicAI ＝ 再帰は2段で打ち止め）。ロールアウト中も賢く打つ前提で精度向上が見込めるが計算量は大幅増。
- **熟練タクティクス（`HeuristicAI`, `enable_tactics`/`finish_priority`/`wall_break`）**: 詰め（先制技で確実にKOできる相手を仕留める=条件C）、崩し（3発で落とせない壁に どくどく＞ちょうはつ＞安全な積み）、数ターンコンボ（ねがいごと→まもるの疑似回復、バトン構築＝積み技/かそく→バトンタッチでエース継承）。いずれも交代判断の後に発火（不利対面では従来どおり交代を優先）。評価：該当archetype使用時はプラス（ねがいごと構築 約+3.7%、バトン構築 約+1.5%）だが、攻撃的構築が多いM-1環境では全体平均は中立。
- **ピボット交代先の選択（バグ修正）**: とんぼがえり/バトンタッチ等の交代先を `_choose_pivot_target` で戦略的に選ぶ（バトンは積みを活かせるエース＝メガ優先、通常ピボットは有利な受け先）。従来は `next_alive_idx` 強制だった。手動対戦の人間選択は従来どおり。

### 5-5. 選出方策（`selection.py`） ※Phase 3実装済み

選出（6体→3体＋先頭）を同時手番ゼロサムゲームとして学習する。選出空間 C(6,3)×先頭=60通りはヒューリスティックで有望な top-k に絞り（`candidate_selections`）、利得行列 `W[i][j]=P(自分が勝つ)` をモンテカルロ推定（`payoff_matrix`）、fictitious play で混合戦略ナッシュ均衡を解く（`solve_zero_sum`、外部依存なし）。`solve_matchup` が1カードを解く。評価：Nash選出は Heuristic選出に約76%勝率。

- **行動方策の差し替え（発展①）**: `payoff_matrix`/`solve_matchup` は `ai_factory`（例: SearchAI）と `with_belief=True` で利得推定時の行動方策を差し替え可能。SearchAI で推定するとデプロイ方策に忠実な均衡が得られる（選出も変化）が計算量は約100倍（既定は高速な HeuristicAI）。
- **メガ前提の評価**: 候補スコア（`_scoring_form`）はメガ石持ちを**メガ後のステータス/タイプ**で評価する。旧実装は素のステータスで足切りしていたため、メガ前提で強いポケモン（スターミー等）が過小評価され見せポケ化していた。
- **副作用禁止（`ai.select_party`）**: 採点は `expected_damage`→`calc_damage` を通るため、半減きのみの消費（`defender.item=None`）・かるわざ（速度+2）・溜め解除が**渡された個体そのもの**に残る。呼び出し側は同じオブジェクトで対戦を始めるので、きのみを失った状態で戦うことになる（実害: `_o1_policy._mcts_vs_dist` で味方のソクノのみが選出評価中に消え、対戦開始時点で持ち物なし。R4 mcts_vs_dist の Rust/Python 乖離として検出）。採点前の状態を保存し、返す直前に必ず巻き戻す（Python `ai.select_party`／Rust `ai::select_party` の両方に同じ包みを置く）。選出結果そのものは不変（R3-sel 4000件で idx 一致）。
- **2メガ選出の抑制（強化）**: 1サイドはメガ1体のみなので、2枚目以降のメガ石持ちは素のフォルムで実質弱く、スロットの機会損失も大きい（実測: P26で2メガ選出 約40%勝率 vs 1メガ 約57%）。候補スコアで「逃したメガ価値＋メガ1枚超過ごとのフラット減点(0.4×平均HP)」を課し、候補top-kを1メガ中心に（P26で7/8）、Nash選出の2メガ重みを 43%→約20% に低減。注: ヒューリスティック `select_party`（自己対戦データ生成・フォールバック用の素朴な選出）はメガ評価を持たず2メガを選びやすいが、デプロイされる選出は学習済みNash（本減点を反映）。

### 5-6. 自己対戦ループ（`train.py`） ※Phase 4実装済み

登録パーティ対ごとに `solve_matchup` を実行し、`(my_id, opp_id)→混合選出戦略` を JSON テーブル（`selection_table.json`）にキャッシュする（`train_selection_table`）。これが「相手構成→選出」の学習成果物。`make_nash_selection` がキャッシュから `SelectionPolicy` を生成（未学習カードはヒューリスティックにフォールバック）。戦闘中の行動方策（SearchAI）は belief で対戦ごとにオンライン適応するため重み学習は行わない。

- **全件並列先計算**: `train_selection_table_parallel`（`python -m simulator.train full [workers]`）が全 C(N,2) カードをマルチプロセス（spawn・読み取り専用DBで安全）で先計算。正本73パーティ＝2628カードを並列で約十数分。先計算しない運用では対戦相手確定時にオンデマンドで `solve_matchup` を解く。

### 5-7. 評価（`evaluate.py`） ※Phase 5実装済み

主要指標を測定：(1) SearchAI vs HeuristicAI 勝率（約77%）、(2) Nash選出 vs Heuristic選出 勝率（約76%）、(3) 統合エージェント (Nash選出+SearchAI) vs ベースライン勝率（約90%）、(4) ダメージ観測による相手耐久推定の誤差縮小（登録スプレッドbelief併用で事前比 約65%改善）。すべて自己対戦の真値で検証。

### 5-8b. 学習価値関数（`features.py`/`value_net.py`/`train_value.py`） ※AlphaZero的アプローチ

コンボを手書きする代わりに、**自己対戦から「長期的価値（勝率）」を学習する評価関数**で探索を導く（AlphaGo/AlphaZeroの核心）。
- **特徴量化（`features.py`）**: 盤面を生特徴（両側のタイプ構成・残HP・能力ランク・状態異常・天候・設置・対面相性・素早さ）にエンコード。天候×タイプ等の相互作用は隠れ層が自分で学習するため、コンボは特徴に書かない。
- **持ち物カテゴリと特徴量v2（`_ITEM_FLAGS` / env `FEAT_V2`）**: 持ち物は個体ごとに効果カテゴリのbitで符号化する。
  既定（`FEAT_V2` 未設定）は**8カテゴリ・全体905次元**で、本番ネット `az_net_np.json` と互換。
  この8カテゴリでは **M-6 上位50種の非メガ持ち物使用率のうち 29%（1,022%pt）が1bitも立たず、ネットからは
  「無持ち物」と同じに見える**（いのちのたま 266%pt・ひかりのねんど 205・ゴツゴツメット 199・ふうせん 85 ほか）。
  実害は測定済み: 同一パーティで持ち物だけ差し替えた ENS スコア差が ±0.0007 以内（勝率換算0.07pt未満）で、
  **スコアラーがゴツゴツメットとたべのこしを区別できない**。その結果、採用は候補生成側の頻度だけで決まり、
  提案キャッシュではギャラドスのゴツゴツメット（実使用37%）採用率が 0% になっていた。
  **2026-09-15 に v2 を既定ONへ変更し、本番ネットも965次元へ差し替えた**（`FEAT_V2=0` で旧905へ戻せるが、
  そのときは Rust `features.rs` の `N_ITEM_FLAGS` も 8 に戻し、905次元のネットへ差し替えること）。
  採用判断: 学習ネット vs 転移ネット（＝旧本番と数値的に同一）600戦で **50.9% p=0.65 の非劣化**。
  勝率の向上は無い（@400の固定点）が、識別率が低い符号化を選ぶ理由が無いため採用した。
  `FEAT_V2=1` で10カテゴリを追加し **965次元**にする（反動火力/画面延長/接触ダメージ返し/じめん無効/天候延長/
  フィールドシード/初撃・抜群強化/能力低下リセット/強制交代/急所上昇）。あわせて、次元を増やさずに
  タイプ強化（きせきのタネ・グランドコート）と半減きのみ（ヨプのみ等）を既存カテゴリへ合流させる。
  識別率は **71% → 99.7%**。カテゴリ間で同じ持ち物が二重に立ってはならない。
  v2 はネット入力を変えるため、**転移学習（新規列を重み0で初期化）＋再学習と Rust `statec.rs` の同期・
  R4-G1 encode ゲート再走がセット**。既定OFFのまま本番へ入れてはならない。
- **技の特徴と特徴量v3（`_M3_*` / env `FEAT_V3`、既定ON）**: 技は「タイプ別の最大威力18 ＋ クラスフラグ10」
  だけで表現していたため、**M-6 上位50種の変化技使用率のうち 32%(4,217%pt) がどのクラスにも入らず、
  ネットからは「持っていない」のと同じに見えていた**（アンコール707 / ちょうはつ426 / 壁3種600 /
  みちづれ298 / みがわり289 %pt ほか）。ユーザー評価軸の「変化技をうまく使えず単に殴るだけ」に
  直結する情報が入力に無い状態だった。v3 で **12次元/個体** を足す（965→**1037**）:
  - 変化技クラス8: 行動制限(ちょうはつ/アンコール) / 壁 / みがわり / 持ち物干渉(トリック) /
    退場支援(みちづれ/おきみやげ/バトンタッチ等) / 遅延回復(ねがいごと/いたみわけ) /
    リセット・タイプ改変(くろいきり/みずびたし) / 場操作(トリックルーム/各フィールド)
  - 最大威力技の量的4: 命中率 / 反動の有無 / 自分の能力下降の有無 / 連続技の期待倍率。
    これが無いと **オーバーヒート(130) が かえんほうしゃ(90) より常に良く見える**（C2段下降・命中90が不可視）。
  あわせて次元を増やさず コスモパワー・せいちょう を `_M_SETUP` に合流。被覆は **68% → 99.5%**。
  `_M3_RECOIL` は `battle._apply_recoil` と、`_M3_HITS` は `battle._calc_hits` と同じ集合にすること
  （ずれるとネットが見る性質が実挙動と食い違う）。
  Rust `features.rs` の `F3_*` は **ビット12以降**を使う（9〜11 は `F_MH2/F_MH3/F_MH25` が使用済み。
  最初に9から振って衝突させた）。`FEAT_V3=0` で965、`FEAT_V2=0 FEAT_V3=0` で905へ段階的に戻せる。
- **価値ネット（`value_net.py`）**: pure Python の小型MLP（1隠れ層・SGD・学習率減衰）。状態→P(side1勝利) を予測。numpy非依存・重みはJSON保存。
- **学習（`train_value.py`）**: 自己対戦の各ターン状態を最終勝敗でラベル付けして学習。現状 held-out 精度 約72%（中盤盤面から勝者を予測）。
- **探索統合**: `SearchAI(value_fn=...)` で打ち切り葉を学習価値で評価。深さ8＋価値が深さ50ロールアウトとほぼ同等（価値ブートストラップ）。
- **反復ループ（`selfplay_value_iteration`）**: 価値誘導の自己対戦→価値再学習を繰り返す（AlphaZero）。反復＋探索で未知のコンボ（雨・バトン等）を方策が発見し価値が学習する設計。
- **現状の限界**: 1反復・HeuristicAI由来データでは雨等のシナジー価値は弱く不安定（データ被覆不足）。本格的な創発には多反復＋探索＋計算資源が必要（pure Python・GPU無しで規模制約）。フレームワークは正しく整備済み。

### 5-8c. 方策＋価値ネットと PUCT-MCTS（`alphazero.py`/`train_alphazero.py`） ※完全AlphaZero構造

価値だけでなく**方策ヘッド**を加え、探索の事前確率に使う（AlphaZeroの完全構造）。
- **行動語彙（固定12次元）**: 技4枠×{通常,メガ}=8、控え交代3枠、わるあがき1。`action_to_index`/`legal_actions_indexed`。
- **二頭ネット `PolicyValueNet`**: 共有1隠れ層 → 価値(P(side1勝利)) ＋ 方策(合法手上のprior)。pure Python・SGD。
- **PUCT-MCTS（`mcts_search`/`PVMCTSAI`）**: 自分の意思決定ノードの木を張り、`Q + c·P·√ΣN/(1+N)` で選択、価値ネットで葉評価、訪問回数最大の手を選ぶ。相手は belief から決定化して固定方策で環境として扱う（imperfect-info対応）。
- **学習（`train_alphazero.py`）**: 自己対戦で (状態, 取った行動, 合法手, 勝敗) を集め、方策=行動の模倣(交差エントロピー)・価値=勝敗(BCE) を同時学習。現状 価値精度約71%・方策top1一致約51%。
- **評価**: 探索量に比例して強くなる（PVMCTS vs HeuristicAI が n_sims=30→80 で 45%→57%）。AlphaGo同様、探索量＋自己対戦反復に応じて向上する性質を確認。
- **現状の限界**: pure Python・GPU無し・少反復・低 n_sims では、終局までロールアウトする `SearchAI`（約67%）には未到達。本格的な創発・超越には大規模自己対戦反復＋大きなネット＋多数 n_sims が必要。構造は完全に整備済み。

    努力値の合計の割合の DB との差（10pt）を警告に追加。シーズン固定版（v41）と datapack は変えていない（週次の版 M-6/2026-10-04 を作っただけ）。
  - **型プール＋ダメージ観測**: 型の重み＝出現率 × Π(観測したダメージを再現できる尤度)（`PokemonBelief.pool_weights`）。受けたダメージ（相手の耐久）と与えたダメージ（相手の火力・火力アイテム）の両方を、持ち物・特性・性格・努力値が同じ組（プロファイル、1種あたり中央値489通り）ごとに乱数16通りで計算し、`observe_damage` と同じ平滑化（`_EPS`）で掛ける。どの型でも再現できない観測は捨てる。観測は `dmg_obs` に溜め、型を引くとき（初回参照時）にまとめて反映する。再計算で対戦の乱数を消費しない（Rust `PokemonBelief::pool_weights` と 1:1）
  - **観測の粒度は実機に合わせる**（`hp_pct`/`obs_match`・Rust も同じ）: 相手のHPは実機で整数％でしか見えない（四捨五入で表示）。与えたダメージは攻撃前後の表示の差で、前後の丸めで最大±1%ずれるので、候補のダメージ％が観測の±1%以内なら一致とする。自分のHPは実数で見えるので、受けたダメージは整数で一致を取る。以前はどちらも最大HP比を0.1%単位で比べており、相手側は実機より細かく絞りすぎ（誤入力や丸めで正解を消す）、自分側は実機より粗かった
  - **ダメージ観測に使う一撃の条件**（`observe_damage`/`observe_damage_dealt` 共通・Rust も同じ）: 1回攻撃・急所でない・受けた側が生き残り HP が2以上。連続技は合計しか見えないのに1発分の計算と比べており、倒した一撃やタスキ/がんじょうで耐えた一撃は残りHPで打ち切られる（HPを超えた 290% のような値で EV/性格を絞っていた）
  - **観測時点の状態を載せて逆算する**（`pub_state`/`with_state`・Rust も同じ）: 候補の個体は素の状態で作るので、行動前の相手の能力変化・状態異常・メガ進化・残りHP割合（`battle._pre_att/_pre_def`）を載せてから計算する。自分側の個体も行動前の状態に戻す（りゅうせいぐん等で技の後に能力が下がる）。以前はつるぎのまい後の火力を「A特化の型」、メガ後の能力値を「再現不可」と取り違えていた。EV/性格候補（`cands`）と型プールの両方に効く
  - **行動順の観測**（`_observe_order`）: 特性込みの優先度（`_priority_base`＝せんせいのツメ以外。いたずらごころ・はやてのつばさ等）が同じときだけ使う。トリックルーム・おいかぜ中、あとだし/クイックドロウ/はやあし/ぶきようが場にいるときは速度以外で順番が決まるので使わない。型プールでは候補自身の持ち物（スカーフ等）込みの実効速度で先後を判定する
  - **発動しなかった持ち物**（`observe_absent_item`、たべのこしで回復しなかった等）は型プールの候補からも外す（`absent_items`）
  - **判明した技は自分の技だけ**: わるあがき・まねっこでコピーした技は `on_move` しない（型の候補と矛盾して全滅していた）
  - **縛られた技が使えないとき**（こだわり・アンコール・あばれる中にかなしばり等）: 他の技は選べず、わるあがき（または交代）になる（`ai._filter_valid_by_lock`・Rust `filter_valid_by_lock`）。以前は他の技へ逃がしており、こだわり中に技を撃ち分けられていた。縛られた技自体を持っていない場合（決定化で技構成が入れ替わった等）は縛りなし扱い
  - **発動しなかったことからの否定（追加）**: 接触技を当てたのに反動が無かった→ゴツゴツメットではない（`_disclose_contact_reaction` と同じ条件）。ターン終了で表示HPが確実に半分を下回っている（実HP≤最大/2 かつ 49%未満）のにきのみが発動しなかった→オボンのみ/オレンのみではない（きんちょうかんで食べられない時は推論しない）。型プール相手の較正で、これらの持ち物を「予測60%以上で当たり半分」と過信していた。Rust も同じ
  - **ふうせんの否定**: ふうせんは登場時に表示される（`ENTRY_VISIBLE_ITEMS`）ので、初登場時に表示が無ければふうせんではない（`PokeKnowledge.no_balloon`→`absent_items`）。M-5 実構築でふうせんを予測60%以上で16件外していた。Rust も同じ
  - **同じ持ち物はパーティに1つ**（上位構築410党で重複1件）: 判明した味方の持ち物は、他の個体の `absent_items` に加えて候補から外す（`OpponentBelief.observe_disclosure`）。トリック等で入れ替わった後（`item_epoch`>0）の持ち物は元の持ち物ではないので使わない。Rust も同じ
  - **こだわりアイテムの否定**: 交代せずに違う技を2種類使ったら、こだわりスカーフ/ハチマキ/メガネではない（`observe_absent_item`）。ねごとで出た技は数えない（`_via_call`）。登場し直すと数え直す（`_entry_moves`）。持ち物が途中で変わったら数え直す（トリックでスカーフを渡された等。`_entry_item`）。Rust も同じ
  - **整合チェック**: 探索（MCTS）の中で引いた型と相手の真の型が判明情報と矛盾しないかを Rust が数える（`det_consist_take`。`_local/ai_work/scripts/detconsist.py`）。greedy 対戦の信念が正解を消していないかは `_local/ai_work/scripts/belief_invariants.py`
  - **技選びの観測**（型プール経路。`observe_choice`→`PokemonBelief._apply_choice`・Rust `ObsKind::Choice`）: 相手が攻撃技を自分で選んだとき（変化技・先制技・こだわり/アンコール/あばれるで縛られている時は除く）、候補の型ごとに攻撃技の期待ダメージ（連続技は期待回数を掛ける）を計算し、選んだ技×1.5 がその型の最大に届かなければ重みを ×0.3（`CHOICE_BETA`）。選んだ技で倒せるならどの型でも同じ。相手は戦略で弱い技も選ぶので消しはしない。持ち物の無いなげつけるは威力0として扱う。同じ受け手に同じ技を選び続けたのは実質1回の判断なので、(技, 受け手) ごとに1回だけ数える。**既定で無効、`POOL_CHOICE=1` で有効**（M-5 実構築相手の的中で効果が見えなかった：乱数3通りで型全一致 −0.2pt・技1本あたり −0.3pt、種ごとのばらつき ±0.7pt）
  - **メガ進化後**: 判明する特性はメガ後のもの（ボーマンダ→スカイスキン）だが、型プールはメガ前の特性で持つ。判明したメガ石の型は特性で弾かない（弾くと全滅して周辺分布に落ちていた）。決定化の特性は判明した特性を優先する（Rust がメガ前の特性で上書きしており Python と食い違っていた）
  - 検証: `_rust_engine/belief_parity.py`（greedy 対戦に両側の信念を付け、終局後の P1 の信念＝EV/性格の事後・型プール重み・判明情報を Python と Rust で突き合わせる。Rust 側は `BELIEF_PROBE=1` と `belief_probe_take`）
- `BUILD_MAP_RATE` / `PokemonBelief.map_rate`: この確率で**最尤型**を返す（0=常に抽選・従来）。
  情報は**超加法的**で、部分的に正しい相手はほとんど価値が無い（実測: 持ち物だけ開示 −0.4pt /
  技だけ +1.7pt / 性格+努力値だけ −2.3pt に対し、**全部開示は +10.0pt**）。毎回抽選すると
  「どれも少しずつ違う相手」ばかりになるので、最尤型に寄せて「完全に正しい相手」での
  シミュレーションを一定割合作るほうがよい。型丸ごとの一致率（観測なし）: 13.4% → **24.0%**
- **信念のシーズン**は `_default_belief_season()`＝`BELIEF_SEASON > POOL_SEASON > M-6`。
  Rust も `sim.rs::belief_season()` で同じ解決順（以前は両方 "M-2" 固定）。
  ただしシーズンの選択自体は的中率をほとんど動かさない（M-2/M-3/M-5/M-6 で技4本一致 6.2〜7.1%）
- 評価用プール（`_m6_pool`）の型は信念に入れない。本番の相手はプールだが、入れると自己対戦A/Bが不当に有利になる

#### Rust 側の学習・評価インターフェース（2026-09-18 追加・すべて既定OFF）

- `search.rs`: `NODE_TRACE=<割合>` で**探索木の内部ノード**も教師にする。展開時の特徴ベクトルは

  （`w[0]` の総和 / `n[0]` の総和・探索側視点）と組にして吐く。訪問12未満は値が不安定なので捨てる。

    「選ばれなかった手の先」。分布が違ううえ、**兄弟局面どうしの差**を一度も学習していない。
    データ量が37万件で飽和したのは、同じ種類の情報しか増えていなかったためと考えられる
  - **訪問分布も教師にする**。MCTS はそのノードの下も探索しているので `n[0]` が取れる。

#### 探索の計測用フック（`search_ai.py`・すべて既定OFF＝本番挙動は不変）
伸び代がどこにあるかを「情報を与えたら何pt勝てるか」で測るための実験用スイッチ。2026-09-17 の実測値つき。
- `ORACLE=1` / `SearchAI.oracle`: 相手の型・持ち物・控えを決定化せず真の値で読む（隠れ選出の再サンプルも止める）。
  同一ネット・@400・N=800 で **57.7%**（基準51.8%）＝**型推論の伸び代は +5.9pt**
- `ORACLE_REVEAL` / `SearchAI.oracle_reveal`: 型の**一部だけ**を真値にする（`item` / `ability` / `moves` /
  `spread`（性格+努力値）/ `bench`（隠れ控えの再サンプルを止める）をカンマ区切り）。
  完全情報の +5.9pt が型のどの要素から来ているかを分解して測るためのもの
- `SearchAI.opp_act_hint` / `act_oracle_depth`: 相手が実際に選ぶ手を教える（`_opp_candidates` が深さ
  `act_oracle_depth` 未満で候補を1手に絞る。1=根のみ / 99=全深さ）。型オラクルと併用で **74.4%**
  ＝**相手の行動予測の伸び代は +16.7pt で最大**。単独で使うと決定化した相手の技と対応が取れず
  （実際の技を指すのは52%）誤情報になるので、必ず `oracle=True` と併用すること
- `CAND_TOPK` / `SearchAI.cand_topk`: 根より下で候補を prior 上位K手に刈り込む。K=3/2 とも勝率は動かず（効果なし）
- `SearchAI._track_depth` / `_depth_hist`: 各シミュの到達深さを記録。@400 で平均2.7ターン・@1200 で3.0ターン。
  片側の候補は平均5.0手＝同時手番の分岐25なので、**1ターン深く読むには sims が25倍要る**

- **活性・正規化・最適化は切替式**（2026-09-17）。既定は `act="tanh"` / 正規化なし / `opt="sgd"` ＝**既存ネットの前向き計算は不変**
  （`az_net_np.json` は `act`/`mu` を持たないので読むと必ず従来仕様になる）。
  - `PVNetNP(dim, h1, h2, act="relu", norm=True)` ＋ `fit_norm(X)` ＋ `train_pi(..., optimizer="adam")` で
    ReLU・入力標準化・Adam になる。`save()` は `act`/`mu`/`sd` を書き出し、`load()` がそれに従う
  - **なぜ必要か**: 素のSGD＋tanhでは訓練データに適合できない。方策ターゲット2,000件を 2048x1024・400epoch で
    学習しても訓練 top-1 は 71.1% 止まり（暗記できない）。Adam+ReLU+正規化にすると同条件で **96.5%**。
    このため特徴量追加・容量増・データ増のいずれも勝率に効かなかった（最適化が使い切れていなかった）
  - 適合できるようにすると今度は過学習が露出する（訓練96% / 検証37%）。方策 top-1 の検証値は
    訓練件数に対して 1,000→37%… 9,961→37.3% と**まだ飽和していない**ので、次の律速はデータ量
  - `train_pi(..., value_weight=配列)` でサンプルごとに価値の学習量を変えられる。方策は全局面で学び、
    価値は1対局からk局面だけ、という分離ができる（相関の害を受けるのは価値だけ。π は局面ごとに
    ターゲットが違うので間引く必要がない）
  - `fold_norm()` で入力正規化を第1層に畳み込める（`W1/σ`・`b1 - W1·(μ/σ)`）。第1層は線形なので出力は等価で、
    入力のゼロがゼロのまま残る＝Rust の `rows8_sparse`（非ゼロのみ走査・ビット一致のまま高速化）がそのまま効く。
    Rust へ渡すネットは必ず畳み込んでから保存する
  - `train`/`train_pi` の `ema=d`（>0）でパラメータの指数移動平均を取る。`_step` ごとに
    `shadow = d·shadow + (1-d)·param` を更新し、`apply_ema()` で本体へ書き戻す。
    `_pretrain_value.py` は `EMA>0` のとき best-so-far の復元を行わない（どちらも終盤の振れを均すので両掛けしない）。
    `l2` は重み減衰（env `L2`、既定 1e-5）
  - **注意**: Rust 側のネット前向き（`net.rs`）は tanh 固定。ReLU ネットを本番へ上げる前に Rust を同期すること

- **雨コンボの創発学習**：自己対戦で雨パ（ペリッパー始動）をオーバーサンプリング（=探索/被覆を確保）して学習させると、価値関数が「雨＋水ポケが場に出ている状態」を雨なしより高評価（プローブ平均Δ=+0.11・正の割合100%）。**コンボを手書きせず、自己対戦の勝敗から雨のシナジー価値を自分で学習**できた。
- **重要な知見（被覆＝探索の必要性）**: greedy自己対戦はペリッパーを選出率0%＝雨ゲームが生成されず、雨は学習不能だった。雨を経験させて初めて学習＝AlphaZeroで探索ノイズが創発に不可欠なのと同じ。
- **シングル環境での雨の真の価値（正直な分析）**: 「場に雨があれば水ポケに有利（×1.5）」は正しく学習される一方、**雨起動役ペリッパーを選出するコストは大きく**（強制雨選出 約39%勝率 vs 通常選出 約86%）、シングルでは天候始動に1枠/1ターン割くのは損。AIが雨を選出しないのは正しい判断（雨が支配的なのは全体技を使えるダブル）。

#### 完全自律 AlphaZero ループ（`az_loop.py`）
オーバーサンプリングに頼らず、探索だけで戦略を自力発見する本来のAlphaZero反復：
- **MCTS自己対戦**: 両者が現ネットによるMCTSで指す。根に**Dirichletノイズ**（探索）、**温度サンプリング**（訪問数比例）で多様な手を試す。
- **選出ε探索**（`explore_selection`）: 一定確率で完全ランダム選出（ペリッパー始動等、普段選ばれない構築も試す）→雨ゲーム等が自然に生成される。
- **学習ターゲット**: MCTSの**訪問分布π**（方策）＋最終勝敗（価値）＝本来のAlphaZeroターゲット。`PVNetNP.train_pi`。
- **反復**: 自己対戦→学習→自己対戦… で方策・価値を共進化。`run_loop(fresh=True)` でまっさらから。
- pure Python + numpyネットの小規模デモ。大規模化（多反復・大ネット・多 n_sims）で創発が強まる構造。
