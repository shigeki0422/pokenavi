### データベースの場所（`data.py: DB_PATH`）

`DB_PATH` は既定で **`data.py` 自身の位置から `scripts/pokenavi.db` を相対解決**する（`os.path.dirname(os.path.dirname(os.path.abspath(__file__)))`）。
環境変数 **`POKENAVI_DB`** を設定するとそちらを優先する。

以前は開発機の絶対パス固定だったため、コンテナ（Cloud Run）にそのまま載せると起動時に
`sqlite3.OperationalError: unable to open database file` で落ちた。デプロイ可能性のため相対解決が仕様。

## 1. わざ（技）

### 1-1. 基本仕様

- ダメージ式: `floor(floor(floor(2×Lv/5+2) × 威力 × 攻撃/防御) / 50) + 2`
- Lv固定: **50**
- 乱数: 85〜100% (均一16段階)
- タイプ一致補正 (STAB): ×1.5、てきおうりょく特性時 ×2.0
- 急所倍率: ×1.5、ランクによる確率は下表

| 急所ランク | 発動確率 |
|-----------|--------|
| 0 (標準) | 1/24 |
| +1 (高急所技) | 1/8 |
| +2 (きあいだめ等) | 1/2 |
| +3 以上 | 確定 |

**急所命中時の追加効果（ダメージ×1.5 に加えて）:**
- 攻撃側の攻撃・特攻ランクが**マイナス**の場合、そのランク変化を無視してダメージ計算（プラスのランクは有効）
- 防御側の防御・特防ランクが**プラス**の場合、そのランク変化を無視してダメージ計算（マイナスのランクは有効）

高急所技（ランク+1）: きょうふのつるぎ / からじしボム / フリーズドライ / スラッシュ / カタストロフィ / シャドークロー / ナイトスラッシュ / クロスポイズン / サイコカッター / リーフブレード / ３ぼんのや / ストーンエッジ / ブレイズキック / クラブハンマー / クロスチョップ / つじぎり / ドリルライナー / アクアカッター / エアカッター / ゴッドバード

### 1-7. 2ターン溜め技

1ターン目は「溜め」、2ターン目に攻撃。以下の例外あり：
- ソーラービーム / ソーラーブレード: **晴れ中は即時発動**

### 1-14. あばれ状態

使用すると「あばれ状態」になり、強制的に同じ技を連続で使い続ける。

| 対象技 |
|--------|
| あばれる / げきりん / はなびらのまい / だいふんげき |

**動作仕様**

| フェーズ | 処理 |
|----------|------|
| 初回使用 | `locked_move` に技名をセット、`lock_count` を 2〜3 にランダム設定 |
| 継続ターン | 同じ技を強制使用。`lock_count` を 1 減らす |
| `lock_count` が 0 になった時 | `locked_move` をクリアし、こんらん状態になる（マイペース特性は免疫） |

**制約**
- あばれ状態中（`lock_count > 0`）は他の技を選択不可（UI・AI ともに無効化）
- 交代すると `locked_move` がクリアされる（あばれ状態も解除）
- こんらん発生時、きのみによる回復判定が実行される

## 4. バトルシステム全体仕様

### 4-0. 分析（1v1判定）用の差込口

対戦本体の挙動は変えずに、分析側だけが前提を固定するための差込口を2つ持つ。
既定値では対戦と完全に同じ動作になり、分析中だけ `_mu_engine._enter_fixed()` が差し替える。

| 差込口 | 既定 | 分析時 | 目的 |
|---|---|---|---|
| `damage._ROLL_OVERRIDE` | `None`（16段の乱数） | `0.0`〜`1.0` | 与ダメの下限・上限を出す |
| `battle._HIT_CONTINUE` | `None`（`random.random`） | `lambda: 0.0` | ネズミざんの「もう1発続くか」を必中扱いにする |

`_HIT_CONTINUE` は、**1発ごとに命中判定があり外れるとそこで止まる技**（`battle.ACCURACY_CHAINED`
＝トリプルアクセル・ネズミざん）のための差込口。分析は `check_hit` を必中に固定するので、
これらの技も最大回数まで当たる扱いに揃える。揃えないとネズミざんだけ「1発しか当たらない前提」
になり、主力技が圏外と出る。表示側はこの前提を「最大ヒット時」と注記する。

なお回数そのものが乱数で決まる技（みずしゅりけん等の2〜5回、重み3:3:1:1）は別扱いで、
確定数は最小回数（保証値）、与ダメの幅は最小回数×最低乱数〜最大回数×最高乱数で出す。

### 4-1. 天候効果

| 天候 | 効果 |
|------|------|
| 晴れ (sunny) | ほのお技×1.5、みず技×0.5、ソーラービーム即時発動、かみなり/ぼうふう命中50% |
| 雨 (rain) | みず技×1.5、ほのお技×0.5、かみなり/ぼうふう必中 |
| 砂嵐 (sandstorm) | いわタイプ特防×1.5、毎ターンHP1/16ダメ（いわ/じめん/はがね以外） |
| 雹 (hail) | こおりタイプ防御×1.5（物理）、毎ターンHP1/16ダメ（こおり以外） |

**天候の防御補正の適用順序**：砂の「いわ特防×1.5」・雪の「こおり防御×1.5」は、
**「その技がどの防御実数値を参照するか」が確定した後**に掛ける。
参照能力を差し替える技（サイコショック/サイコブレイク/シークレットソード＝相手のB参照、
せいなるつるぎ/DDラリアット＝相手のBランク変化を無視した素のB参照）でも天候補正は乗る
（これらが無視するのは**ランク変化であって天候補正ではない**）。
判定は「B参照技かD参照技か」で行い、B参照技には雪の補正のみ・D参照技には砂の補正のみが乗る。

### 4-5b. 瀕死交代先の選択（AI）

繰り出し先は**2層**で決める（控えが1匹なら自明・2匹以上の時のみ選択）：
- **実戦の根の決定**：`SearchAI.choose_faint_switch` ＝「交代のみを候補にした通常の価値ベース選択」。各控えを『繰り出し→相手最善応手（K型サンプルの最悪）』で価値ネット評価し最良を選ぶ。反撃KO・受け回し等は価値ネットで一元評価され、個別ルール不要。`Battle.run` が各サイドのAIから取得して使用。
- **シミュ内のロールアウト方策＋フォールバック**：`_best_faint_switch`（高速ヒューリスティック）。タイプ相性に加え**反撃KO**（控えが相手より速く、最大打点で相手の現在HPを削り切れる）を最優先。速さはこだわりスカーフ・まひ・天候特性（すいすい等）を加味。MCTSの各シミュ内faintはこちらを使う（フル探索の再帰を避けるため）。

### 4-6. 行動順と瀕死交代のタイミング

1ターン内で両者は素早さ順に行動する。**ターン中に瀕死になったポケモンの交代（瀕死交代）は、両者の行動が終わったターン終了時に行う**（残ダメージ処理の後）。

- **先攻が自滅した場合**（反動技＝はめつのひかり/すてみタックル/フレアドライブ等の反動、または だいばくはつ/じばく の自爆）、その場は空になる。**後攻の技は対象不在で失敗**し、交代先はそのターンは攻撃を受けない。交代先はターン終了時に着地する（このターンの残ダメージも受けない）。
- **ピボット技（とんぼがえり/ボルトチェンジ/バトンタッチ等）は瀕死ではない自発交代**なので、交代先は通常どおりその場に出て後攻の攻撃を受ける（自滅瀕死と区別する）。
- 実装: `_do_action(defer_self_faint=True)` で先攻の自滅瀕死交代を保留し、後攻は対象不在を検出して失敗。保留分は `_end_of_turn` 末尾の `_faint_switch` が回収する。

## 4. 情報開示（情報の非対称性）

AI同士の対戦学習を見据え、各サイドが相手について「何を知っているか」を `OpponentView`（`opponent_view.py`）で管理する。各 `BattleSide` は `opp_view`（＝そのサイドが相手パーティについて持つ知識）を保持する。

### 4-1. 開示のタイミング
1. **対戦前の見せ合い**: バトル開始時、両者は相手の**候補6体の種族・タイプ**を知る（`team_preview`）。この時点で技・持ち物・特性・努力値は**未開示**。`PokeKnowledge.previewed = True`。
2. **登場時**: 場に出たポケモンを確認（`on_enter`、`seen = True`）。
3. **発動・使用ベースの開示**: 以降は実際に観測された情報のみが開示される。
   - 技を使う → `on_move`（`known_moves` に追加）
   - 持ち物が発動/判明（オボン回復・タスキ・はたきおとす等）→ `on_item`（`known_item`）
   - 特性が発動（がんじょう・いのちのたま反動等）→ `on_ability`（`known_ability`）
   - ダメージを受ける → `on_hp_change`：相手HPの**残り割合**（`hp_fraction`、実数HP/最大HPは不可視。HPバーから観測できる割合のみ）と、**その技で減った割合**（`damage_log` に `{move, attacker, fraction}` を追記）を記録。主にダメージ割合からダメージ計算を逆算し、相手の努力値・性格を類推する用途。

### 4-2. 情報系特性（強制開示）
登場時に相手情報を**強制的に開示**する。`Battle._info_abilities_on_entry`（登場毎に1回、交代でリセット）。
- **おみとおし**: 相手の持ち物を開示（`opp_view.on_item(..., "おみとおし")`）。
- **きけんよち**: 相手が自分に対する**効果抜群技または一撃必殺技**を持つかを判定し、持つなら「危険な技を持つ」と察知（`opp_view.on_anticipation`、`threat_alert = True`）。具体的な技名までは開示しない（本家仕様）。

### 4-3. AI利用
AI（`ai.py`）は `my_side.opp_view` の既知情報のみを参照して意思決定する（`known_moves_of` 等）。未開示情報には依存しない設計。

## 5. 戦略学習環境（自己対戦）

登録済みパーティ同士のAI自己対戦を多数繰り返し、最も勝率の高い戦略を学習させるための環境。アプローチは**探索＋ゲーム理論**（決定化MCTS／expectimax で行動方策、ナッシュ均衡で選出方策）。

### 5-1. 学習対象
1. **選出方策**: 相手の候補6体から、自分の6体のうちどの3体を選び、どれをリード（先頭）にするか（`SelectionPolicy`）。
2. **行動方策**: 毎ターンの行動（技/交代/メガ）。開示情報＋非開示情報の推定（belief）を用い、勝率を最大化する行動を選ぶ。

### 5-2. 環境ハーネス（`env.py`） ※Phase 0実装済み
- **登録テンプレート（正本）**: DB表 `templates` が唯一の正本（M-1上位の情報完全な73構築、`party_id`=順位、型・EV・性格・技確定）。`load_templates`/`load_registered_parties` で読み込み、`build_party`（randomize=False）で確定スペック構築。`build_templates.py` が正本を構築、`generate_ui_templates.py` がUI用の派生一覧（上位100）を生成。旧 `m1_party` 表／`gamewith_parties.json`／手書き `party_templates_new.txt` は本表に一本化し廃止（txtはDB生成物）。データ源は GameWith「上位構築」のため上限は約95件（完全73件）で、ランキング1〜1000位の個人チームは非公開のため取得不可。
- **完全性保証**: `is_complete_party`（種族・技がDB解決可・『不明』なし）で検証。全テンプレートが完全であることを `test_all.py` で固定（誤記・欠落の回帰検出。例: 過去に「エンベルト」=エンペルトの誤記を検出・修正）。
- **選出方策インターフェース**: `SelectionPolicy = (my6, opp6, loader) → 順序付き選出リスト`（先頭=リード）。既定は現行ヒューリスティック（`heuristic_selection`）。学習方策に差し替え可能。
- **対戦実行**: `play_match(p1, p2, loader, ai1, ai2, sel1, sel2)`。行動方策(ai)も差し替え可能。
- **状態クローン／継続**: `Battle.clone()`（deepcopyで独立複製）と `Battle.resume(ai1, ai2)`（見せ合い・初手入場を再実行せず途中状態から継続）。決定化ロールアウトの土台。
- 速度: 単一プロセスで約360試合/秒（10万試合≈5分）。

### 5-3. 推定器（`belief.py`） ※Phase 1実装済み

非開示情報を確率分布として推定する。`PokemonBelief`（相手1体）と `OpponentBelief`（サイド全体＝種族名→PokemonBelief）。

- **技/持ち物/特性**: 使用率DB（`top_moves`/`top_items`/`top_abilities`）を事前分布とし、`opp_view` の開示（`observe_disclosure`）で確定。ダメージ計算は使わない（ユーザー要件「使用率や組み合わせから確率的に警戒」）。`prob_has_move`/`prob_item`/`prob_ability` で参照。
- **EV/性格**: 使用率の `top_evs × top_natures` を候補スプレッドとして列挙（各候補は具体的な防御体を構築）。`observe_damage` で、攻撃側を既知としてダメージ式を逆算し、16段階の乱数ロールで観測割合を再現できる割合を尤度としてベイズ更新。再現不可な観測（マルチヒット・急所等のモデル外）は安全にスキップ。`map_spread`/`spread_posterior`/`expected_stat` で参照。
- **登録スプレッド混入（発展②）**: `OpponentBelief(use_registered=True, 既定)` は `m1_party` の実スプレッド（種族別）を候補に追加する（`registered_spreads_by_species`、キャッシュ付）。このメタは登録パーティ同士のため真の型が候補に入り、ダメージ観測で尤度が集中する。耐久(防御/特防)推定の事後誤差が事前比 約65%改善（混入なしは約10%）。
- **統合**: `BattleSide.belief`（任意）に `OpponentBelief` を付与すると、被ダメージ確定点（`on_hp_change` と同じ箇所）で自動的に `observe_damage` が呼ばれEV/性格を推定。`belief` は対戦状態ではなく意思決定者の知識のため `Battle.clone()`（ロールアウト）には引き継がれない（`__deepcopy__`→None）。
- 既知の制約: 候補防御体は `ensure()` 時点の開示特性/持ち物で1度だけ構築（途中の持ち物判明では再構築しない）。急所観測は非急所モデルと一致せずスキップ。
- 検証: 自己対戦では相手の真の型を我々が知っているため、`map_spread` の的中・事後>事前を直接テストで検証（`test_all.py` 推定器節）。

### 5-4. 行動方策（`search_ai.py`） ※Phase 2実装済み

`SearchAI`：毎ターン、belief から相手の非開示情報（EV/性格・持ち物・特性・未開示技）を K 通りサンプリングして相手を具体化（決定化）し、各候補行動について `Battle.clone()`＋`resume(max_turns=depth)` で短いロールアウトを回して勝率を見積もり、勝率最大（＝負ける確率最小）の行動を選ぶ。

- 観測可能な状態（現在HP割合・ランク変化・状態異常・場・メガ）はクローン元から保持し、非開示情報のみ belief から差し替える。メガ/へんしん中の個体はステータスを再サンプルしない。
- K個の決定化世界を全候補で共通利用（common random numbers）して候補間分散を抑える。ロールアウトの行動は高速な `rollout_ai`（既定 HeuristicAI）。テンプレート未登録種は決定化をスキップ。
- 既定 `rollouts=16, depth=50`。評価：HeuristicAI に対し約77%勝率（登録スプレッドbelief併用時。深さ・Kを上げると向上）。1試合あたり約0.7秒。
- **メガ進化の探索**: メガ可能時は「メガする／しない」を**独立した候補**として勝率比較する（旧実装は `should_mega_evolve` の判断を一律付与するだけだった）。`should_mega_evolve` は「石があれば原則即メガ」に修正（旧実装はメガ種族値÷現行実数値のスケール不一致で発動タイミングが偶然任せ・ハッサム等の物理メガが満タンで発動しないバグがあった）。メガ石名の全角Ｘ/Ｙと半角X/Yの不一致も `normalize_mega_stone` で吸収し、リザードンX/Y等が正しくメガ可能に。
- **再帰探索（発展③, opt-in）**: `make_nested_search` は外側 SearchAI のロールアウト方策に予算を絞った内側 SearchAI を用いる2段ネスト（内側のロールアウトは HeuristicAI ＝ 再帰は2段で打ち止め）。ロールアウト中も賢く打つ前提で精度向上が見込めるが計算量は大幅増。
- **熟練タクティクス（`HeuristicAI`, `enable_tactics`/`finish_priority`/`wall_break`）**: 詰め（先制技で確実にKOできる相手を仕留める=条件C）、崩し（3発で落とせない壁に どくどく＞ちょうはつ＞安全な積み）、数ターンコンボ（ねがいごと→まもるの疑似回復、バトン構築＝積み技/かそく→バトンタッチでエース継承）。いずれも交代判断の後に発火（不利対面では従来どおり交代を優先）。評価：該当archetype使用時はプラス（ねがいごと構築 約+3.7%、バトン構築 約+1.5%）だが、攻撃的構築が多いM-1環境では全体平均は中立。
- **ピボット交代先の選択（バグ修正）**: とんぼがえり/バトンタッチ等の交代先を `_choose_pivot_target` で戦略的に選ぶ（バトンは積みを活かせるエース＝メガ優先、通常ピボットは有利な受け先）。従来は `next_alive_idx` 強制だった。手動対戦の人間選択は従来どおり。

### 5-5. 選出方策（`selection.py`） ※Phase 3実装済み

選出（6体→3体＋先頭）を同時手番ゼロサムゲームとして学習する。選出空間 C(6,3)×先頭=60通りはヒューリスティックで有望な top-k に絞り（`candidate_selections`）、利得行列 `W[i][j]=P(自分が勝つ)` をモンテカルロ推定（`payoff_matrix`）、fictitious play で混合戦略ナッシュ均衡を解く（`solve_zero_sum`、外部依存なし）。`solve_matchup` が1カードを解く。評価：Nash選出は Heuristic選出に約76%勝率。

- **行動方策の差し替え（発展①）**: `payoff_matrix`/`solve_matchup` は `ai_factory`（例: SearchAI）と `with_belief=True` で利得推定時の行動方策を差し替え可能。SearchAI で推定するとデプロイ方策に忠実な均衡が得られる（選出も変化）が計算量は約100倍（既定は高速な HeuristicAI）。
- **メガ前提の評価**: 候補スコア（`_scoring_form`）はメガ石持ちを**メガ後のステータス/タイプ**で評価する。旧実装は素のステータスで足切りしていたため、メガ前提で強いポケモン（スターミー等）が過小評価され見せポケ化していた。
- **2メガ選出の抑制（強化）**: 1サイドはメガ1体のみなので、2枚目以降のメガ石持ちは素のフォルムで実質弱く、スロットの機会損失も大きい（実測: P26で2メガ選出 約40%勝率 vs 1メガ 約57%）。候補スコアで「逃したメガ価値＋メガ1枚超過ごとのフラット減点(0.4×平均HP)」を課し、候補top-kを1メガ中心に（P26で7/8）、Nash選出の2メガ重みを 43%→約20% に低減。注: ヒューリスティック `select_party`（自己対戦データ生成・フォールバック用の素朴な選出）はメガ評価を持たず2メガを選びやすいが、デプロイされる選出は学習済みNash（本減点を反映）。

### 5-6. 自己対戦ループ（`train.py`） ※Phase 4実装済み

登録パーティ対ごとに `solve_matchup` を実行し、`(my_id, opp_id)→混合選出戦略` を JSON テーブル（`selection_table.json`）にキャッシュする（`train_selection_table`）。これが「相手構成→選出」の学習成果物。`make_nash_selection` がキャッシュから `SelectionPolicy` を生成（未学習カードはヒューリスティックにフォールバック）。戦闘中の行動方策（SearchAI）は belief で対戦ごとにオンライン適応するため重み学習は行わない。

- **全件並列先計算**: `train_selection_table_parallel`（`python -m simulator.train full [workers]`）が全 C(N,2) カードをマルチプロセス（spawn・読み取り専用DBで安全）で先計算。正本73パーティ＝2628カードを並列で約十数分。先計算しない運用では対戦相手確定時にオンデマンドで `solve_matchup` を解く。

### 5-7. 評価（`evaluate.py`） ※Phase 5実装済み

主要指標を測定：(1) SearchAI vs HeuristicAI 勝率（約77%）、(2) Nash選出 vs Heuristic選出 勝率（約76%）、(3) 統合エージェント (Nash選出+SearchAI) vs ベースライン勝率（約90%）、(4) ダメージ観測による相手耐久推定の誤差縮小（登録スプレッドbelief併用で事前比 約65%改善）。すべて自己対戦の真値で検証。

### 5-8b. 学習価値関数（`features.py`/`value_net.py`/`train_value.py`） ※AlphaZero的アプローチ

コンボを手書きする代わりに、**自己対戦から「長期的価値（勝率）」を学習する評価関数**で探索を導く（AlphaGo/AlphaZeroの核心）。
- **特徴量化（`features.py`）**: 盤面を生特徴（両側のタイプ構成・残HP・能力ランク・状態異常・天候・設置・対面相性・素早さ）にエンコード。天候×タイプ等の相互作用は隠れ層が自分で学習するため、コンボは特徴に書かない。
- **価値ネット（`value_net.py`）**: pure Python の小型MLP（1隠れ層・SGD・学習率減衰）。状態→P(side1勝利) を予測。numpy非依存・重みはJSON保存。
- **学習（`train_value.py`）**: 自己対戦の各ターン状態を最終勝敗でラベル付けして学習。現状 held-out 精度 約72%（中盤盤面から勝者を予測）。
- **探索統合**: `SearchAI(value_fn=...)` で打ち切り葉を学習価値で評価。深さ8＋価値が深さ50ロールアウトとほぼ同等（価値ブートストラップ）。
- **反復ループ（`selfplay_value_iteration`）**: 価値誘導の自己対戦→価値再学習を繰り返す（AlphaZero）。反復＋探索で未知のコンボ（雨・バトン等）を方策が発見し価値が学習する設計。
- **現状の限界**: 1反復・HeuristicAI由来データでは雨等のシナジー価値は弱く不安定（データ被覆不足）。本格的な創発には多反復＋探索＋計算資源が必要（pure Python・GPU無しで規模制約）。フレームワークは正しく整備済み。

### 5-8c. 方策＋価値ネットと PUCT-MCTS（`alphazero.py`/`train_alphazero.py`） ※完全AlphaZero構造

価値だけでなく**方策ヘッド**を加え、探索の事前確率に使う（AlphaZeroの完全構造）。
- **行動語彙（固定12次元）**: 技4枠×{通常,メガ}=8、控え交代3枠、わるあがき1。`action_to_index`/`legal_actions_indexed`。
- **二頭ネット `PolicyValueNet`**: 共有1隠れ層 → 価値(P(side1勝利)) ＋ 方策(合法手上のprior)。pure Python・SGD。
- **PUCT-MCTS（`mcts_search`/`PVMCTSAI`）**: 自分の意思決定ノードの木を張り、`Q + c·P·√ΣN/(1+N)` で選択、価値ネットで葉評価、訪問回数最大の手を選ぶ。相手は belief から決定化して固定方策で環境として扱う（imperfect-info対応）。
- **学習（`train_alphazero.py`）**: 自己対戦で (状態, 取った行動, 合法手, 勝敗) を集め、方策=行動の模倣(交差エントロピー)・価値=勝敗(BCE) を同時学習。現状 価値精度約71%・方策top1一致約51%。
- **評価**: 探索量に比例して強くなる（PVMCTS vs HeuristicAI が n_sims=30→80 で 45%→57%）。AlphaGo同様、探索量＋自己対戦反復に応じて向上する性質を確認。
- **現状の限界**: pure Python・GPU無し・少反復・低 n_sims では、終局までロールアウトする `SearchAI`（約67%）には未到達。本格的な創発・超越には大規模自己対戦反復＋大きなネット＋多数 n_sims が必要。構造は完全に整備済み。

#### numpy版（`az_np.py`/`train_az_np.py`）＝大規模化と雨コンボ創発の実証
- `PVNetNP`：numpyでベクトル化した二頭ネット（ミニバッチSGD）。学習が分→秒に高速化（6000試合×40epochを約28秒）。`PVMCTSAI` から同一インターフェースで利用可。
- **雨コンボの創発学習**：自己対戦で雨パ（ペリッパー始動）をオーバーサンプリング（=探索/被覆を確保）して学習させると、価値関数が「雨＋水ポケが場に出ている状態」を雨なしより高評価（プローブ平均Δ=+0.11・正の割合100%）。**コンボを手書きせず、自己対戦の勝敗から雨のシナジー価値を自分で学習**できた。
- **重要な知見（被覆＝探索の必要性）**: greedy自己対戦はペリッパーを選出率0%＝雨ゲームが生成されず、雨は学習不能だった。雨を経験させて初めて学習＝AlphaZeroで探索ノイズが創発に不可欠なのと同じ。
- **シングル環境での雨の真の価値（正直な分析）**: 「場に雨があれば水ポケに有利（×1.5）」は正しく学習される一方、**雨起動役ペリッパーを選出するコストは大きく**（強制雨選出 約39%勝率 vs 通常選出 約86%）、シングルでは天候始動に1枠/1ターン割くのは損。AIが雨を選出しないのは正しい判断（雨が支配的なのは全体技を使えるダブル）。

#### 完全自律 AlphaZero ループ（`az_loop.py`）
オーバーサンプリングに頼らず、探索だけで戦略を自力発見する本来のAlphaZero反復：
- **MCTS自己対戦**: 両者が現ネットによるMCTSで指す。根に**Dirichletノイズ**（探索）、**温度サンプリング**（訪問数比例）で多様な手を試す。
- **選出ε探索**（`explore_selection`）: 一定確率で完全ランダム選出（ペリッパー始動等、普段選ばれない構築も試す）→雨ゲーム等が自然に生成される。
- **学習ターゲット**: MCTSの**訪問分布π**（方策）＋最終勝敗（価値）＝本来のAlphaZeroターゲット。`PVNetNP.train_pi`。
- **反復**: 自己対戦→学習→自己対戦… で方策・価値を共進化。`run_loop(fresh=True)` でまっさらから。
- pure Python + numpyネットの小規模デモ。大規模化（多反復・大ネット・多 n_sims）で創発が強まる構造。
- **計測知見（ボトルネックと並列化）**: 自己対戦1反復の時間内訳は **シミュレーション100% / 学習0%（0.03秒）**。よってGPU/PyTorchはここでは無効（ネット学習は既に一瞬で、律速はpure Pythonのバトル計算。単一状態のMCTS推論はむしろtorchで遅くなる）。実用的な大規模化は**自己対戦のマルチプロセス並列**（`run_loop_parallel`、spawn・読み取り専用ネットをワーカーへ配布）。14コアで約7倍速。`python -m simulator.az_loop [iters] [games] [n_sims]`。

### 5-8. 戦略の言語化（`explain.py`）

学習した戦略を自然言語で説明する。
- **選出方策**: 学習済み選出テーブル（混合戦略）を `describe_party_strategy` で要約。各6体の選出率（コア/状況選出/ほぼ不採用）、先頭傾向、相手別の推奨選出と「固定選出／要混合」の別を言語化する。
- **行動方策**: `SearchAI.score_actions` が各候補行動の推定勝率を返し、`explain_turn` が「どの手が何%で最も負けにくいか」を出力する（探索の判断根拠の可視化）。

### 5-9. Webシミュレータ統合（`sim_server.py`）

ブラウザのバトルシミュレータ（`scripts/sim_ui/index.html` → FastAPI バックエンド）の **AI を学習済みAIに置換**：
- **観戦バトル（`/api/battle/stream`）・手動対戦の相手（`/api/manual/*`）** の行動方策を `SearchAI`（サーバ用に rollouts=8, depth=30 で応答性確保）に変更。両サイドに `OpponentBelief` を付与し、被ダメージ割合からEV/性格をオンライン推定。
- **選出**を学習済みナッシュ均衡から引く（`learned_select`）。ブラウザが送る6体スペックを `template_index`（spec集合→party_id）で正本テンプレに対応づけ、`selection_table.json` のカードがあれば混合戦略から選出。未対応カードはヒューリスティック選出にフォールバック。
- **モンテカルロ勝率（`/api/simulate`）** は試行数が多く SearchAI が非現実的なため高速な HeuristicAI を維持（統計推定用途）。
